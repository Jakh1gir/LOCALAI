# База данных

Одна база SQLite в режиме WAL с включёнными внешними ключами (DATA-10). Источник истины — миграции в `engine/migrations/`; здесь объяснено, что где лежит и почему. Пишет в базу только сервер, через пакет `engine`.

Этот документ описывает миграцию `0001_core` (этап 1). Таблицы доступа, документов, памяти ИИ, импорта и схем добавляются миграциями своих этапов.

## Принципы

- **Запись — документ JSON.** Значения полей записи лежат в одном столбце `records.doc`. Новый тип, поле или реестр создаётся данными, без изменения схемы базы (DATA-01).
- **Ключ поля постоянен.** В документе значение лежит под ключом поля (`f1`, `f2`, … или заданным явно). Название поля можно менять сколько угодно — документы не трогаются.
- **Ссылки хранятся как ID.** Значение справочника и объект ККС записаны в документе своим UUID. Переименование значения или кода сразу видно во всех записях.
- **Пустого значения нет.** Незаполненное поле в документе отсутствует; пустая строка и пустой список не хранятся.
- **Время** — строка UTC вида `2026-11-17T09:30:00.000Z`.

## Поля типа

| Вид (`kind`) | Что хранится в документе | Примечание |
| --- | --- | --- |
| `text` | строка | до 20 000 символов |
| `integer` | целое число | |
| `number` | число | запятая в дробной части принимается на входе |
| `boolean` | `true` / `false` | |
| `date` | строка `ГГГГ-ММ-ДД` | на входе принимается и `ДД.ММ.ГГГГ` |
| `choice` | UUID значения справочника | режим ввода: `strict` — только из списка, `suggest` — новое значение добавляется |
| `kks` | UUID объекта ККС | роль связи: `object`, `signal`, `route_start`, `route_end`, `route_via`, `related` |

Флаги поля:

- `multiple` — несколько значений; в документе список, порядок сохраняется. Для поля ККС это точки маршрута.
- `required` — обязательно при создании; при правке обязательное поле нельзя очистить.
- `searchable` — значение попадает в полнотекстовый индекс.
- `filterable`, `sortable` — для поля создаётся индекс по выражению `json_extract(doc, '$.<ключ>')` (DATA-03). Индекс общий для ключа, начинается с реестра и покрывает только действующие записи. Поля ККС ищутся по таблице связей и отдельного индекса не получают.

Вид, ключ и признак `multiple` после создания поля не меняются. Поле не удаляется, а уходит в архив: значения в записях остаются, поле перестаёт показываться, приниматься и искаться.

## Записи и история

- `records.seq` — внутренний номер записи; наружу отдаётся только UUID `id`. Так же устроен `datasets.seq`: короткий номер стоит в каждой записи и в каждом индексе вместо 36-символьного UUID.
- `records.version` растёт на единицу при каждом изменении. Изменяющий запрос несёт ожидаемую версию; несовпадение — ошибка `version_conflict` (DATA-04).
- Правка, которая ничего не меняет, версию не создаёт.
- `record_versions.changes` — разница версии: `{"ключ": [было, стало]}`, `null` означает «пусто». Любая версия восстанавливается обратным ходом от текущего документа (DATA-05). У первой версии разница пуста: её значения получаются тем же обратным ходом, поэтому создание записи не хранит документ дважды.
- Откат создаёт новую версию со значениями выбранной; история не переписывается.
- Архив записи — отметка `archived_at` и новая версия. Связи ККС и история при архиве сохраняются (DATA-08).

## ККС

- Объект ККС имеет постоянный UUID. Код хранится в исходном написании (`code`) и в нормализованном виде (`code_norm`): убраны внешние пробелы и различие регистра. Ведущие нули, внутренние разделители и различия алфавитов сохраняются.
- Нормализованный код уникален в пределах площадки; то же правило действует для псевдонимов. Код не может совпасть с псевдонимом другого объекта, и наоборот.
- Переименование сохраняет UUID и связи; прежний код становится псевдонимом вида `former` (DATA-06).
- Архив объекта сохраняет связи и удерживает код. Новая связь с архивным объектом требует его восстановления.
- `record_kks_links` строится по полям вида `kks`: запись, ключ поля, позиция, объект, роль. Позиция уникальна внутри поля записи; одна связь (объект, роль, запись, позиция) не повторяется (DATA-07). Один и тот же объект на другой позиции маршрута допустим.

## Поиск

`record_fts` — индекс FTS5 с триграммным разбором без хранения текста. В него попадает то, что видит человек: текст, числа, даты в двух написаниях, названия значений справочников и коды ККС. Текст сворачивается к нижнему регистру, «ё» приравнена к «е». После переименования значения справочника или кода ККС индекс затронутых записей обновляется в той же транзакции.

## Аудит и идемпотентность

- Каждое действие оставляет строку в `audit_log` в той же транзакции, что и само изменение: кто, когда, что, над чем. Пакетная загрузка — одна строка с числом записей и числом созданных объектов ККС.
- `idempotency_keys` хранит результат изменяющего запроса по паре «область, ключ». Повтор с тем же ключом возвращает прежний результат; тот же ключ с другим содержимым — ошибка `idempotency_mismatch` (API-06).

## Миграции

- Файлы `NNNN_название.sql`, номера подряд. Применённая миграция не редактируется.
- Перед изменением существующей базы создаётся её копия рядом с файлом базы и проверяется `PRAGMA integrity_check`; без исправной копии миграция не начинается (DATA-11).
- Миграция применяется одной транзакцией: при ошибке схема остаётся прежней.
- База, созданная более новой версией программы, не открывается (`schema_newer`).
