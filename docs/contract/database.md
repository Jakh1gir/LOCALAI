# База данных

Одна база SQLite в режиме WAL с включёнными внешними ключами (DATA-10). Источник истины — миграции в `engine/migrations/`; здесь объяснено, что где лежит и почему. Пишет в базу только сервер, через пакет `engine`.

Этот документ описывает миграции `0001_core`, `0002_import_runs`, `0003_kks_link_index` (этап 1), `0004_access`, `0005_allowed_ips` и `0006_purge_right` (этап 2), `0007_links`, `0008_chat` и `0009_import` (этап 3), `0010_documents` (этап 4). Таблицы документов, памяти ИИ и схем добавляются миграциями своих этапов.

## Принципы

- **Запись — документ JSON.** Значения полей записи лежат в одном столбце `records.doc`. Новый тип, поле или реестр создаётся данными, без изменения схемы базы (DATA-01).
- **Ключ поля постоянен.** В документе значение лежит под ключом поля (`f1`, `f2`, … или заданным явно). Название поля можно менять сколько угодно — документы не трогаются.
- **Ссылки хранятся как ID.** Значение справочника и объект ККС записаны в документе своим UUID. Переименование значения или кода сразу видно во всех записях.
- **Пустого значения нет.** Незаполненное поле в документе отсутствует; пустая строка и пустой список не хранятся.
- **Время** — строка UTC вида `2026-11-17T09:30:00.000Z`.

## Поля типа

| Вид (`kind`) | Что хранится в документе | Примечание |
| --- | --- | --- |
| `text` | строка | до 20 000 символов |
| `integer` | целое число | |
| `number` | число | запятая в дробной части принимается на входе |
| `boolean` | `true` / `false` | |
| `date` | строка `ГГГГ-ММ-ДД` | на входе принимается и `ДД.ММ.ГГГГ` |
| `choice` | UUID значения справочника | режим ввода: `strict` — только из списка, `suggest` — новое значение добавляется |
| `kks` | UUID объекта ККС | роль связи: `object`, `signal`, `route_start`, `route_end`, `route_via`, `related` |

Флаги поля:

- `multiple` — несколько значений; в документе список, порядок сохраняется. Для поля ККС это точки маршрута.
- `required` — обязательно при создании; при правке обязательное поле нельзя очистить.
- `searchable` — значение попадает в полнотекстовый индекс.
- `filterable`, `sortable` — для поля с одним значением создаётся индекс по выражению `json_extract(doc, '$.<ключ>')` (DATA-03). Индекс общий для ключа, начинается с реестра и покрывает только действующие записи. Поля ККС ищутся по таблице связей и её индексу. Для поля с несколькими значениями индекса по выражению нет: SQLite не индексирует элементы списка внутри JSON, поэтому фильтр по такому полю перебирает записи реестра через `json_each`. Это отступление от DATA-03 записано в решениях владельца.

Вид, ключ и признак `multiple` после создания поля не меняются. Поле не удаляется, а уходит в архив: значения в записях остаются, поле перестаёт показываться, приниматься и искаться.

## Один ККС — много строк

- **Уникальное поле** (`fields.unique_values`). `record_unique (dataset_seq, field_key, value, record_seq)` с первичным ключом по первым трём столбцам: повтор значения в реестре невозможен на уровне базы. `value` — текст через `fold` (без учёта регистра и «ё»), число — JSON, дата — строка, ККС — UUID объекта. Строки есть только у действующих записей: архив их снимает, возврат из архива ставит снова. Удаление записи удаляет их каскадом.
- **Ссылка на запись** (`fields.kind = 'record'`, `fields.target_type_id`). В документе — UUID записи-цели (или список). `record_links (record_seq, field_key, ordinal, target_seq)`: удаление записи-источника удаляет её ссылки каскадом, а запись-цель, на которую ссылаются, база удалить не даст. Индекс `ix_links_target` даёт обратные ссылки.
- **Контакт** (`fields.contact_for`) — у текстового поля ключ поля `kks` или `record` того же типа; по нему граф подписывает связь.
- **Правило кода** — `kks_rules (scope, signal_pattern)`, строка `scope = '*'`; по умолчанию `X[A-Z][0-9]{2}`.
- Миграция `0007` пересоздаёт `fields` с новым видом и столбцами: на эту таблицу никто не ссылается внешним ключом, строки переносятся как есть.

## Записи и история

- `records.seq` — внутренний номер записи; наружу отдаётся только UUID `id`. Так же устроен `datasets.seq`: короткий номер стоит в каждой записи и в каждом индексе вместо 36-символьного UUID.
- `records.version` растёт на единицу при каждом изменении. Изменяющий запрос несёт ожидаемую версию; несовпадение — ошибка `version_conflict` (DATA-04).
- Правка, которая ничего не меняет, версию не создаёт.
- `record_versions.changes` — разница версии: `{"ключ": [было, стало]}`, `null` означает «пусто». Любая версия восстанавливается обратным ходом от текущего документа (DATA-05). У первой версии разница пуста: её значения получаются тем же обратным ходом, поэтому создание записи не хранит документ дважды.
- Откат создаёт новую версию со значениями выбранной; история не переписывается. Откат подчиняется правилам обычной правки: значение должно подходить полю, обязательное поле не очищается, архивное значение справочника и архивный объект ККС заново не ставятся — их сначала восстанавливают. Поля в архиве откат не меняет. Версию, которую откатить нельзя, можно смотреть.
- Версия, которой нет в истории (Local_DB не сохранила её снимок), не восстанавливается: чтение и откат такой версии дают `version_missing`.
- Архив записи — отметка `archived_at` и новая версия. Связи ККС и история при архиве сохраняются (DATA-08).

## ККС

- Объект ККС имеет постоянный UUID. Код хранится в исходном написании (`code`) и в нормализованном виде (`code_norm`): убраны внешние пробелы и различие регистра. Ведущие нули, внутренние разделители и различия алфавитов сохраняются.
- Нормализованный код уникален в пределах площадки; то же правило действует для псевдонимов. Код не может совпасть с псевдонимом другого объекта, и наоборот.
- Переименование сохраняет UUID и связи; прежний код становится псевдонимом вида `former` (DATA-06).
- Архив объекта сохраняет связи и удерживает код. Новая связь с архивным объектом требует его восстановления.
- `record_kks_links` строится по полям вида `kks`: запись, ключ поля, позиция, объект, роль. Первичный ключ «запись, поле, позиция»: на одной позиции поля один объект (DATA-07). Один и тот же объект может стоять в разных полях записи и на разных позициях одного поля — например, точка маршрута, через которую кабель проходит дважды.

## Поиск

`record_fts` — индекс FTS5 с триграммным разбором без хранения текста. В него попадает то, что видит человек: текст, числа, даты в двух написаниях, названия значений справочников и коды ККС. Текст сворачивается к нижнему регистру, «ё» приравнена к «е». После переименования значения справочника или кода ККС индекс затронутых записей обновляется в той же транзакции.

## Аудит и идемпотентность

- Каждое действие оставляет строку в `audit_log` в той же транзакции, что и само изменение: кто, когда, что, над чем. Пакетная загрузка — одна строка с числом записей и числом созданных объектов ККС.
- **События** (API-09) — те же строки `audit_log`: `seq` служит курсором для `GET /events`. Отдельной таблицы событий нет, поэтому событие не расходится с изменением.
- `idempotency_keys` хранит результат изменяющего запроса по паре «область, ключ». Повтор с тем же ключом возвращает прежний результат; тот же ключ с другим содержимым — ошибка `idempotency_mismatch` (API-06).

## Доступ

- **Роли — данные.** Права привязаны к `roles.id`; переименование роли ничего не меняет (ROLE-02). Отключённая роль (`archived_at`) не даёт входа её пользователям.
- **Матрица прав** — строки `role_permissions (role_id, scope, target, action)`:

  | `scope` | `target` | `action` |
  | --- | --- | --- |
  | `section` | имя раздела: `admin`, `structure`, `kks`, `ai`, `tools`, `timesheet`, `backups`, `chat`, `chat_write`, `chat_moderate`, `documents`, `worker` | `use` |
  | `dataset` | UUID реестра или `*` — все реестры | `view`, `create`, `edit`, `archive`, `purge`, `import`, `export` |
  | `field` | UUID поля | `hidden`, `readonly` — ограничения поверх прав на реестр |
  | `doc_type` | UUID типа документов или `*` — все типы | `view` |

  Допустимые сочетания проверяет ограничение `CHECK` таблицы. Строка по UUID реестра или поля не удаляется вместе с ними: реестры и поля уходят в архив, а не удаляются.
- Право `purge` добавлено миграцией `0006`: она пересоздаёт таблицу с новым `CHECK` и выдаёт право на все реестры ролям с разделом «Администрирование».
- Разделы общего чата добавлены миграцией `0008`: `chat` и `chat_write` — всем ролям, что были в базе, `chat_moderate` — ролям с разделом «Администрирование». Новые роли получают их от администратора.
- **Стартовые роли** «Администратор», «Инженер», «Наблюдатель» создаёт миграция `0004` (ROLE-10). Пользователей миграция не создаёт: стартовых паролей нет (SEC-03).
- **Пароль** хранится хэшем scrypt с солью и параметрами: `scrypt$15$8$1$<соль>$<хэш>`, около 32 МиБ памяти и 0,1 с на проверку. Требование SEC-01 называет Argon2; для него нужен сторонний пакет, а `engine` использует только стандартную библиотеку. Хэш несёт свои параметры, поэтому смена алгоритма или параметров произойдёт при следующем входе каждого пользователя, без сброса паролей. Отступление записано в решениях владельца.
- `users.login_norm` — логин без учёта регистра, уникален. `must_change_password` — пароль временный, его надо сменить при входе (ROLE-06). `failed_logins` и `locked_until` — счётчик неверных паролей подряд и время, до которого вход закрыт.
- **Сессия** хранится как SHA-256 токена (`sessions.token_hash`): копия базы не даёт войти. `expires_at` — 12 часов от входа, `last_seen_at` обновляется не чаще раза в минуту; сессия без запросов 15 минут закрыта (SEC-02). Истёкшие сессии удаляются при каждом входе.
- `allowed_ips.network` — сеть в каноническом виде (`10.0.5.0/24`, отдельный адрес — `/32`), уникальна. Адрес самого сервера разрешён всегда.
- Резервная копия — не таблица, а зашифрованный файл `*.localai-backup` в папке копий сервера: внутри полная копия базы вместе с пользователями, ролями и журналом. Формат — в `server/backups.py`.
- Ключ идемпотентности хранится с UUID пользователя в области (`scope`): одинаковые ключи разных пользователей не пересекаются. Ответы с временным паролем сохраняются без него.

## Общий чат

- Сообщение не удаляется из базы: удаление автором ставит `deleted_at`, скрытие модератором — `hidden_at`, `hidden_by` и причину. Текст остаётся для модератора и истории.
- Правка переносит прежний текст в `chat_message_versions` с прежним номером версии; `chat_messages.version` растёт с каждой правкой, удалением, скрытием и возвратом.
- `chat_fts` хранит свёрнутый текст (нижний регистр, «ё» = «е»); rowid — `chat_messages.seq`.
- Ссылки на ККС и записи в базе не хранятся: они разбираются при чтении с правами читающего.

## Документы

- Содержимое файла лежит в `files/<2 знака хэша>/<SHA-256>` рядом с базой: один файл на хэш (DATA-09). Строка `files` не удаляется, пока на неё ссылается документ; прежние файлы заменённых документов остаются — история версий.
- **Резервная копия базы папку `files` пока не включает** (KNOW-11) — это следующий шаг Claude.
- `chunks.version` — версия документа, из которой взят фрагмент. Поиск берёт фрагменты только текущей версии; замена и архив удаляют фрагменты сразу.
- `jobs.target_version` — версия документа для задачи. Результат чужой версии не принимается.
- Миграция `0010` добавила раздел `documents` ролям «Администратор» и «Инженер» и типы «Документ» и «Схема».

## Импорт Excel

- Книга пакета лежит файлом `<id>.xlsx` в папке `imports` рядом с базой и удаляется через сутки или после применения. В резервную копию не входит.
- `import_batches.plan_cursor` — номер строки журнала при планировании, `plan_schema` — ревизии схем типов: по ним применение узнаёт устаревший план (IMP-04).
- `import_rows.cells` хранит значения строки книги: применение берёт их отсюда (IMP-03). После применения строки удаляются, отчёт остаётся в `import_batches.report`.
- `import_profiles.signature` — SHA-256 свёрнутых заголовков листа в их порядке: по нему профиль предлагается следующей книге.

## Перенос из других систем

- Перенесённые записи сохраняют исходные UUID, номера версий, авторов и время. Версии загружаются функцией `engine.records.load`; она проверяет вид и принадлежность значений, но не требует обязательных полей: старые данные не теряются из-за правил, появившихся позже.
- Происхождение версии — столбец `record_versions.origin`: `user`, `system` для действий в LOCALAI, `localdb` для перенесённых из Local_DB. Автор перенесённой версии записан текстом с пометкой «(из Local_DB)» (MIG-09).
- Повторный перенос дописывает к записи только версии новее её текущей, и только если последняя версия тоже пришла из Local_DB. Перед записью проверяется, что новые разницы продолжают текущую историю (`engine.records.extend`).
- Типы, поля, справочники и их значения при переносе получают UUID из источника, поэтому повторный перенос находит их без отдельной таблицы соответствий. Реестр из режима Local_DB получает UUID, вычисленный из UUID таблицы и значения режима.
- `import_runs` — одна строка на применённый перенос: источник, площадка, кто и когда, позиция в журнале источника (`audit_cursor`) и краткий отчёт. Пробный прогон строк не оставляет.

## Миграции

- Файлы `NNNN_название.sql`, номера подряд. Применённая миграция не редактируется.
- Перед каждой миграцией существующей базы создаётся её копия рядом с файлом базы и проверяется `PRAGMA integrity_check`; без исправной копии миграция не начинается (DATA-11). Новой пустой базе копии не нужны.
- Каждая миграция применяется отдельной транзакцией. При сбое база остаётся на последней применённой схеме, и копии перед каждой миграцией серии сохраняются. После успешной серии остаётся только копия перед первой миграцией.
- База, созданная более новой версией программы, не открывается (`schema_newer`).
