# API версии 1 — этапы 1 и 2

**Состояние: действует.** Маршруты реализованы в `server/routes/`; машинное описание строится из кода и лежит в [openapi.json](openapi.json). Тест сверяет список маршрутов в этом документе с кодом в обе стороны: маршрут без описания здесь или описание без маршрута не проходит проверку. Импорт, документы и ИИ добавляются перед своими этапами.

Интерфейс может работать на заглушке по этому документу. Язык запросов и формат записи описаны в [query-language.md](query-language.md), хранение — в [database.md](database.md).

## Общие правила

- Основа пути: `/api/v1`. Запросы и ответы — JSON в UTF-8.
- Идентификаторы — UUID. Время — строка UTC `2026-11-17T09:30:00.000Z`.
- Список без страниц отдаётся как `{"items": [...]}`; страницы записей — как описано в языке запросов.
- **Ожидаемая версия.** Изменение записи несёт `expected_version`. Если запись успели изменить, сервер отвечает `409 version_conflict` и текущей версией в `details.current_version`; интерфейс показывает отличия, а не затирает чужую правку (DATA-04).
- **Идемпотентность.** Каждый изменяющий запрос обязан нести заголовок `Idempotency-Key` (до 128 символов); без него — `400 idempotency_key_required`. Повтор с тем же ключом возвращает прежний ответ и ничего не меняет; тот же ключ с другим телом — `409 idempotency_mismatch` (API-06). Чтение (`GET`, а также `POST …/records/query`, `…/records/count` и `…/records/values`) ключа не требует. Вход, выход, смена своего пароля и действия с резервными копиями ключа не требуют и не повторяются по нему: в отпечатке запроса оказался бы пароль, а результат копии — файл, а не строки базы. Ключ принадлежит пользователю: тот же ключ у другого пользователя — отдельный запрос.
- **Одно действие — одна транзакция.** При любой ошибке не остаётся ни частичных данных, ни строки аудита.
- **Вход обязателен.** Кроме `POST /auth/login` и `GET /system/health`, каждый маршрут требует сессии и права, объявленного у маршрута (`x-permission` в `openapi.json`); маршрут без права не собирается (API-02). Права и правила — в разделе «Вход и права».
- Тело запроса — до 10 МиБ; больше — `413 request_too_large`. Лишние поля в теле отклоняются.
- Ответ без тела — `204`. Непредвиденная ошибка — `500` с кодом `internal` без подробностей; подробности пишутся в журнал сервера.

## Ошибка

```json
{"error": {"code": "value_number", "message": "Ожидается число", "field": "f3", "details": {"row": 30}}}
```

`code` — устойчивый машинный код, `message` — текст для человека на русском, `field` — ключ поля или параметра, `details` — дополнительные данные (номер строки пакета, текущая версия). `field` и `details` могут отсутствовать (API-08).

| HTTP | Когда | Примеры кодов |
| --- | --- | --- |
| 400 | Неверные данные или запрос | `backup_password`, `backup_corrupt`, `backup_format`, `schema_newer`, `network_invalid`, `password_wrong`, `password_too_short`, `password_same`, `login_invalid`, `login_taken`, `permission_invalid`, `request_invalid`, `request_json`, `idempotency_key_required`, `value_required`, `value_number`, `value_precision`, `value_out_of_range`, `value_date`, `value_choice`, `value_choice_archived`, `field_unknown`, `field_archived`, `field_change`, `name_taken`, `name_empty`, `query_invalid`, `kks_archived`, `kks_unknown`, `kks_too_long`, `rollback_invalid`, `dataset_parent_archived` |
| 404 | Объект или адрес не найден | `backup_not_found`, `route_not_found`, `record_not_found`, `dataset_not_found`, `type_not_found`, `kks_not_found`, `version_missing` |
| 401 | Нет входа, сессия закрыта или истекла; неверный логин или пароль | `auth_required`, `session_invalid`, `session_expired`, `login_failed` |
| 403 | Недостаточно прав; учётная запись заблокирована; нужно сменить временный пароль; адрес не в списке разрешённых | `forbidden` (`details.permission`), `field_forbidden` (`field`), `user_blocked`, `password_change_required`, `address_not_allowed` |
| 409 | Конфликт с текущим состоянием | `version_conflict`, `record_archived`, `kks_code_taken`, `idempotency_mismatch`, `last_admin`, `network_lockout` |
| 413 | Тело запроса больше 10 МиБ | `request_too_large` |
| 429 | Слишком много неудачных входов | `login_locked` (`details.locked_until`), `login_throttled` |

## Вход и права

### Сессия

| Метод и путь | Тело запроса | Ответ |
| --- | --- | --- |
| `POST /auth/login` | `{login, password}` | права пользователя (как `GET /auth/me`); cookie сессии |
| `POST /auth/logout` | — | — ; сессия закрыта, cookie стёрта |
| `GET /auth/me` | — | `{user, role, must_change_password, permissions, session_expires_at}` |
| `POST /auth/password` | `{current_password, new_password}` | права пользователя; остальные его сессии закрыты |
| `GET /auth/permissions` | — | что можно выдать роли: `sections`, `dataset_actions`, `field_limits`, `doc_type_actions` с подписями |

- Сессия передаётся в cookie `localai_session` (`HttpOnly`, `SameSite=Strict`, `Secure` по HTTPS) или в заголовке `Authorization: Bearer <токен>`. Токен в базе хранится только как SHA-256 (SEC-01).
- Сессия живёт до 12 часов и закрывается после 15 минут без запросов (SEC-02); тогда — `401 session_expired`, интерфейс показывает вход.
- Неверный логин и неверный пароль дают одинаковый ответ `401 login_failed`. После 5 неверных паролей подряд вход в учётную запись закрыт на 15 минут — `429 login_locked`; с одного адреса — не больше 20 неудачных входов за 15 минут — `429 login_throttled`.
- После сброса пароля пользователь входит временным паролем и до смены видит только `/auth/*`; остальные маршруты отвечают `403 password_change_required` (ROLE-06).
- Пароль — от 12 до 256 символов и не содержит логина.
- Права читаются из базы на каждый запрос: изменение роли, её прав, блокировка действуют на открытые сессии со следующего запроса (ROLE-09).
- `must_change_password` и `permissions` в ответе входа подсказывают интерфейсу, какие экраны показывать; проверяет права всегда сервер.

`permissions` в ответе:

```json
{
  "sections": ["admin", "kks", "structure"],
  "datasets": {"*": ["view"], "<UUID реестра>": ["create", "edit"]},
  "fields": {"<UUID поля>": "hidden", "<UUID поля>": "readonly"}
}
```

### Права маршрутов

| Право (`x-permission`) | Кто проходит | Маршруты |
| --- | --- | --- |
| `public` | все | `POST /auth/login`, `GET /system/health` |
| `self` | вошедший, в том числе с временным паролем | `/auth/logout`, `/auth/me`, `/auth/password` |
| `session` | вошедший | чтение структуры и каталога ККС, `GET /auth/permissions`, `GET /events` |
| `section.structure` | роль с разделом «Структура» | изменение площадок, типов, полей, реестров, справочников |
| `section.kks` | роль с разделом «Каталог ККС» | изменение каталога ККС |
| `section.admin` | роль с разделом «Администрирование» | пользователи, роли, журнал, разрешённые адреса |
| `section.backups` | роль с разделом «Копии» | резервные копии |
| `section.chat` | роль с разделом «Общий чат: читать» | лента, поиск, история своих сообщений, отметка прочитанного |
| `section.chat_write` | роль с разделами «Общий чат: читать» и «…: писать» | отправка, правка и удаление своих сообщений |
| `section.chat_moderate` | роль с разделом «Общий чат: скрывать чужие сообщения» | скрытие и возврат сообщений |
| `section.documents` | роль с разделом «Документы» | загрузка, замена, архив, привязки, решения по упоминаниям ККС |
| `section.worker` | служебная учётная запись процесса схем | захват и завершение фоновых задач, скачивание файла документа |
| `section.knowledge` | роль с разделом «Знания» | подтверждение и отклонение заметок, очередь проверки, словарь станции |
| `dataset.view`, `.create`, `.edit`, `.archive`, `.purge` | роль с этим действием над реестром из пути (или реестром записи) | маршруты записей, `GET /datasets/{id}` |

- `GET /datasets` показывает только реестры, которые роль может видеть; роли с разделом «Структура» или «Администрирование» — все реестры: им нужно вести структуру и выдавать права на реестры, записи которых они сами не читают. Карточка ККС считает связи только в таких реестрах.
- **Ограничения полей.** Скрытое поле (`hidden`) не приходит в документах записей, истории, версиях и в `GET /types/{id}` (кроме ролей с разделом «Структура» или «Администрирование»); по нему нельзя фильтровать и сортировать (`400 query_invalid`), поиск его не видит. Изменение скрытого или закрытого для правки поля (`readonly`) — `403 field_forbidden` с ключом поля; откат, который изменил бы такое поле, тоже отклоняется. Если у роли есть скрытые поля реестра, поиск идёт перебором видимых значений, а не по индексу: он медленнее, а даты ищутся в виде `2024-03-15`.
- Импорт и экспорт (`dataset.import`, `dataset.export`), разделы «ИИ», «Инструменты», «Табель» и права на типы документов хранятся в матрице уже сейчас и начнут действовать вместе со своими маршрутами.

### Пользователи и роли

Все маршруты — `section.admin`.

| Метод и путь | Тело запроса | Ответ |
| --- | --- | --- |
| `GET /roles` | — | роли с числом пользователей `users` |
| `POST /roles` | `{name, description?, copy_from?}` | роль с правами; `copy_from` — UUID роли, права которой копируются |
| `GET /roles/{id}` | — | роль и `permissions` — список `{scope, target, action}` |
| `PATCH /roles/{id}` | `{name?, description?}` | роль; права и журнал остаются за UUID роли (ROLE-02) |
| `POST /roles/{id}/archive`, `/restore` | — | роль; пользователи отключённой роли не входят, их сессии закрыты |
| `PUT /roles/{id}/permissions` | `{permissions: [{scope, target, action}]}` | роль; матрица заменяется целиком, в журнал пишется разница |
| `GET /users` | — | учётные записи |
| `POST /users` | `{login, name, role_id}` | учётная запись и `temporary_password`, `201` |
| `GET /users/{id}` | — | учётная запись |
| `PATCH /users/{id}` | `{name?, role_id?}` | учётная запись |
| `POST /users/{id}/block`, `/unblock` | — | учётная запись; блокировка закрывает сессии |
| `POST /users/{id}/reset-password` | — | учётная запись и `temporary_password`; сессии пользователя закрыты |

Строка матрицы прав:

| `scope` | `target` | `action` |
| --- | --- | --- |
| `section` | `admin`, `structure`, `kks`, `ai`, `tools`, `timesheet`, `backups` | `use` |
| `dataset` | UUID реестра или `*` — все реестры, в том числе будущие | `view`, `create`, `edit`, `archive`, `purge` (удалять из архива окончательно), `import`, `export` |
| `field` | UUID поля | `hidden` — не видеть, `readonly` — не править; без строки поле подчиняется правам на реестр |
| `doc_type` | `*` (типы документов — с этапа 4) | `view` |

- Учётная запись: `{id, login, name, role_id, role_name, must_change_password, blocked_at, locked_until, last_login_at, password_changed_at, created_at, updated_at}`. Пароль и его хэш не выдаются никогда (ROLE-07).
- `temporary_password` показывается один раз — в ответе на создание и сброс; повтор того же запроса по ключу идемпотентности его не возвращает.
- Изменение, после которого не останется ни одного активного пользователя с разделом «Администрирование» (блокировка, смена роли, отключение роли, снятие права), отклоняется — `409 last_admin` (ROLE-08).
- Стартовые роли «Администратор», «Инженер», «Наблюдатель» создаются вместе с базой и изменяются как любые другие (ROLE-10). Пользователей в новой базе нет: первого администратора создаёт установщик (SEC-03):

```
python -m server.admin --db localai.sqlite3 create-admin --login admin --name "Иванов И. И."
```

Пароль вводится дважды или передаётся первой строкой ввода с `--password-stdin`. Команда `reset-password --login …` выдаёт временный пароль, если единственный администратор забыл свой.

## Резервные копии

Все маршруты — `section.backups`. Копии лежат в папке сервера (по умолчанию `backups` рядом с базой; `python -m server --backups <папка>`).

| Метод и путь | Тело запроса | Ответ |
| --- | --- | --- |
| `GET /backups` | — | копии от новых к старым |
| `POST /backups` | `{password, label?}` | копия, `201` |
| `GET /backups/{name}/file` | — | файл копии (`application/octet-stream`) |
| `POST /backups/{name}/restore` | `{password}` | `{restored, protective_backup, schema_version, files_added}` |

Копия в списке: `{name, size, created_at, label, protective, schema_version, database_id, app_version, files, files_missing}`. Копия содержит базу и файлы документов (KNOW-11): `files` — сколько файлов в копии, `files_missing` — сколько файлов, на которые ссылается база, не нашлось на диске при упаковке. При восстановлении недостающие файлы добавляются в хранилище (`files_added`), имеющиеся не трогаются; копии старого формата (только база) восстанавливаются как раньше. `protective: true` — защитная копия, сделанная сервером перед восстановлением; признак записан в заголовке копии, подпись «Перед восстановлением» его не даёт. У копий, сделанных до этого признака, — `false`. Файл, который не читается как копия, приходит с полем `error`.

- **Копия зашифрована** (SEC-09): AES-256-GCM, ключ из пароля через Argon2id. Пароль — от 12 символов, в базе не хранится; без него копию не восстановить. Время, подпись и версия схемы читаются без пароля, чтобы показать список.
- Копия делается из согласованного снимка базы и проверяется (`integrity_check`) до шифрования. Работа других пользователей во время копии не останавливается.
- **Восстановление** сначала расшифровывает и проверяет копию: неверный пароль — `400 backup_password`, повреждённый или обрезанный файл — `400 backup_corrupt`, копия от более новой программы — `400 schema_newer`. Пока проверка не пройдена, база не меняется.
- Перед заменой базы текущее состояние упаковывается **тем же паролем** в защитную копию с подписью «Перед восстановлением» (SEC-09); ошибочное восстановление отменяется восстановлением из неё.
- После восстановления схема доводится до текущей версии, а **все сессии закрываются**: входят заново, по учётным записям из копии. В журнал восстановленной базы пишется `backup.restore` с именем защитной копии.
- Копию с другой машины кладут в папку копий сервера; загрузки файла через API нет: тело запроса ограничено 10 МиБ.

## Структура

| Метод и путь | Тело запроса | Ответ |
| --- | --- | --- |
| `GET /sites` | — | список площадок |
| `POST /sites` | `{name}` | площадка |
| `PATCH /sites/{id}` | `{name}` | площадка |
| `GET /types` | — | список типов без полей |
| `POST /types` | `{name, description?}` | тип |
| `GET /types/{id}` | — | тип с полями в порядке показа |
| `PATCH /types/{id}` | `{name}` | тип |
| `POST /types/{id}/archive` | — | — ; отклоняется, пока у типа есть действующие реестры |
| `POST /types/{id}/fields` | поле, см. ниже | поле |
| `PATCH /fields/{id}` | `{name?, position?, required?, searchable?, filterable?, sortable?, input_mode?, unique?, contact_for?}` | поле |
| `POST /fields/{id}/archive`, `/restore` | — | поле |
| `GET /datasets?site_id=&type_id=` | — | список реестров |
| `POST /datasets` | `{site_id, type_id, name}` | реестр |
| `GET /datasets/{id}` | — | реестр |
| `PATCH /datasets/{id}` | `{name}` | реестр |
| `POST /datasets/{id}/archive`, `/restore` | — | реестр |
| `GET /dictionaries` | — | список справочников |
| `POST /dictionaries` | `{name}` | справочник |
| `PATCH /dictionaries/{id}` | `{name}` | справочник |
| `GET /dictionaries/{id}/values?archived=` | — | значения справочника |
| `POST /dictionaries/{id}/values` | `{value, synonyms?}` | значение |
| `PATCH /dictionary-values/{id}` | `{value?, synonyms?, archived?}` | значение |

Поле при создании:

```json
{
  "name": "Изготовитель",
  "kind": "choice",
  "key": null,
  "multiple": false,
  "required": false,
  "searchable": true,
  "filterable": true,
  "sortable": false,
  "dictionary_id": "…",
  "input_mode": "suggest",
  "kks_role": null,
  "unique": false,
  "target_type_id": null,
  "contact_for": null
}
```

`kind` — `text`, `integer`, `number`, `boolean`, `date`, `choice`, `kks`, `record`. `key` можно не задавать: сервер выдаст `f1`, `f2`, …; заданный ключ — латинские строчные буквы, цифры и `_`, до 32 символов. `dictionary_id` и `input_mode` нужны только для `choice`, `kks_role` — только для `kks`, `target_type_id` — только для `record`. Вид, ключ, `multiple` и `target_type_id` после создания не меняются. В ответе поле несёт `unique_values`, `target_type_id`, `contact_for`.

- **`unique`** (DATA-12) — значение не повторяется среди действующих записей реестра. Текст сравнивается без учёта регистра и «ё», ККС — по объекту. Повтор — `409 value_not_unique`, в `details.record_id` — запись, у которой значение уже есть. Только для одного значения вида `text`, `integer`, `number`, `date`, `kks`. Включение у поля с повторами — `409 unique_has_duplicates`. Запись в архиве значение не держит; при её возврате значение должно быть свободно.
- **`record`** (DATA-13) — ссылка на запись типа `target_type_id` на той же площадке. Значение при записи — `{"id": "<UUID>"}`, UUID или значение уникального поля записи-цели: `"cable": "5011"` находит кабель по номеру. Не найдено — `400 record_link_missing`; подходит несколько — `400 record_link_ambiguous`; цель в архиве — `400 record_link_archived`. Сортировать по ссылке нельзя. Запись, на которую ссылаются, окончательно не удаляется — `409 record_referenced`.
- **`contact_for`** (DATA-14) — у текстового поля: ключ поля `kks` или `record` того же типа. Значение подписывает связь этого поля в графе: клемма, жила, вход блока. У многозначных полей пары берутся по порядку значений.

Объекты структуры в ответах:

```json
{"id": "…", "name": "ТЭЦ-1", "archived_at": null, "created_at": "…", "updated_at": "…"}
```

Тип дополнительно несёт `description`, `schema_rev` и, в `GET /types/{id}`, список `fields`. Реестр несёт `site_id` и `type_id`. Интерфейс может хранить схему типа у себя и перечитывать её, когда `schema_rev` изменился.

| `POST /datasets/{id}/records/query` | запрос на языке запросов | страница: `items`, `next_cursor`, `refs` |
| `POST /datasets/{id}/records/count` | тот же запрос без `sort`, `limit`, `cursor` | `{"count": 1234}` |

| `GET /records/{id}` | — | `{record, refs, backlinks, backlink_refs}`; `backlinks` — до 200 записей видимых реестров, которые ссылаются на эту: `[{record_id, dataset_id, field_key}]` |
| `PATCH /records/{id}` | `{expected_version, values}` | запись |
| `POST /records/{id}/archive`, `/restore` | `{expected_version}` | запись |
| `GET /records/{id}/history` | — | список версий от новой к старой |
| `GET /records/{id}/versions/{n}` | — | `{doc, refs}` — документ на версии `n` |
| `POST /records/{id}/rollback` | `{expected_version, to_version}` | запись с новой версией |

`values` — объект «ключ поля → значение»:

- простые виды — значение или текст, который сервер приведёт (`"12,5"`, `"15.03.2024"`, `"да"`);
- `choice` — `{"id": "<UUID>"}` либо название или синоним значения;
- `kks` — `{"id": "<UUID>"}` либо код; неизвестный код создаёт объект ККС на площадке реестра;
- поле с несколькими значениями — список; порядок сохраняется;
- `null` или пустая строка очищают поле.

В `PATCH` передаются только изменяемые поля. Если правка ничего не меняет, версия остаётся прежней и запись возвращается как есть.

**Значения поля** (`…/records/values`, право `dataset.view`) — список для фильтра столбца: самые частые значения поля и число записей с каждым при тех же условиях, что у подсчёта. `limit` — от 1 до 200, по умолчанию 50; `distinct` — сколько всего разных значений. Запись без значения попадает в группу `value: null`; запись с многозначным полем считается в каждом своём значении один раз. ID значений справочника и ККС подписаны в `refs`. Скрытое от роли поле — `400 query_invalid`, поле `field`.

**Пакетная правка** (`…/records/batch-update`, право `dataset.edit`, F-007) записывает одни и те же `values` в выбранные записи. До 5000 записей за раз, все из реестра пути; у каждой своя ожидаемая версия. Каждая изменённая запись получает новую версию и строку истории; запись, где значения уже такие, не меняется. Ошибка на любой записи отменяет всю правку; в `details` — `row` (номер в `items`, с нуля) и `record_id`. В журнал пишутся `record.update` по каждой записи и `record.update_many` по реестру.

**Окончательное удаление** (`…/records/purge`, право `dataset.purge`, F-009) удаляет записи из архива вместе с историей, связями ККС и строкой поиска. Действующую запись сначала отправляют в архив, иначе — `409 record_not_archived`. Объекты ККС остаются в каталоге. В журнале остаются `record.purge` (ID записи и её последняя версия, без значений) и `record.purge_many`. Действие необратимо; право по умолчанию есть только у ролей с разделом «Администрирование».

Версия в истории:

```json
{
  "version": 2,
  "op": "update",
  "changes": {"f2": ["Насос", "Насос ПЭН-1"], "f3": [500, null]},
  "actor_id": "…",
  "actor_label": "Инженер Петров",
  "origin": "user",
  "at": "2026-11-17T10:02:11.512Z",
  "restored_from": null
}
```

`op` — `create`, `update`, `archive`, `restore`, `rollback`, `import`. В `changes` пара «было, стало»; `null` — пусто. У отката `restored_from` — номер версии, значения которой возвращены.

- Смена `code` — переименование: UUID и связи сохраняются, прежний код становится псевдонимом. Занятый код — `409 kks_code_taken` с `details.kks_id` владельца.

Код сигнала не становится объектом каталога: `resolve` находит по нему объект. Правило, которое подходит к пустой строке или не разбирается, — `400 kks_rule_invalid`.

## Импорт Excel

Мастер из шести шагов (ТЗ 6.1). План хранится на сервере: клиент не присылает строки на применение (IMP-03). Пакет импорта видит только тот, кто загрузил книгу; чужой — `404`. Книга живёт сутки (`expires_at`), потом план нужно строить заново с новой загрузкой.

| Метод и путь | Тело запроса | Ответ |
| --- | --- | --- |
| `POST /imports?name=` | файл `.xlsx` как есть (`application/octet-stream`), до 25 МиБ | пакет, `201` |
| `GET /imports/{id}` | — | пакет |
| `GET /imports/{id}/preview?sheet=&header_row=&dataset_id=` | — | `{sheet, header_row, headers, rows, sample, suggested, profiles}` |
| `POST /imports/{id}/plan` | `{sheet, header_row?, mode, …}` | пакет со сводкой плана |
| `GET /imports/{id}/rows?action=&after=&limit=` | — | `{items, more, last}` — строки плана по номеру строки листа |
| `PUT /imports/{id}/rows/{row}/decision` | `{decision: "skip" \| "apply"}` | строка плана |
| `POST /imports/{id}/apply` | `{save_profile?}` | отчёт |
| `GET /import-profiles` | — | `{items: [{id, name, settings, created_by, updated_at}]}` |
| `DELETE /import-profiles/{id}` | — | — |

**Пакет:** `{id, file: {name, size}, status, sheets, settings, summary, report, created_at, planned_at, applied_at, expires_at}`. `status` — `uploaded`, `planned` или `applied`. `sheets` — листы книги: `{name, rows, columns, top, header_row}`, где `top` — первые 30 строк для выбора строки заголовков, а `header_row` — догадка сервера.

**Подсказки** (`preview.suggested`):
- `mode` — `magnet`, если на листе есть коды сигналов, иначе `records`;
- `layout` — роли столбцов по магниту ККС (IMP-14);
- `mapping` — столбцы, совпавшие с полями реестра `dataset_id` по названию или ключу; столбцы шаблона выгрузки «UUID» и «Версия» — как `@id` и `@version`.

`profiles` — профили, сохранённые для книги с теми же заголовками (IMP-08).

**План** (`mode`):
- **`records`** — в существующий реестр: `{dataset_id, mapping: {столбец: ключ поля | "@id" | "@version"}, key?}`. Нужно право `import` на реестр (IMP-12).
  - Запись опознаётся по `@id` из шаблона выгрузки, затем по `key` — уникальному полю (DATA-12). Без ключа строки только добавляются (IMP-01).
  - Ключом не может быть неуникальное поле и код ККС объекта (`400 import_key`, IMP-02).
  - Пустая ячейка значение не стирает; отсутствие строки в книге ничего не архивирует (IMP-07).
  - В поле с несколькими значениями ячейка делится по «;», как её пишет выгрузка.
  - Скрытое от роли поле или поле только для чтения в сопоставлении — `403 field_forbidden`.
- **`new_type`** — «Создать тип и загрузить»: `{new_type: {type_name, dataset_name, site_id, fields: [{column, name?, kind?, unique?}]}}`.
  - `kind` — `text` (по умолчанию), `integer`, `number`, `date`, `boolean` или `kks`; первое поле с `unique` становится ключом.
  - Тип, поля и реестр создаются только при применении. Нужен раздел «Структура».
- **`magnet`** — таблица сигналов раскладывается магнитом ККС (IMP-13…16): `{name, site_id?, layout?}`.
  - Таблица с кодами сигналов ложится в реестры «`name` — сигналы» и «`name` — кабели», таблица аппаратов — в реестр «`name`».
  - Без `layout` берётся подсказка магнита. Код тот же, что у переноса выгрузки Local_DB (MIG-17).
  - Нужен раздел «Структура» или готовые реестры раскладки с правом `import`.

**Сводка плана** (`summary`): `{mode, rows, counts: {create, update, unchanged, conflict, error}, headers}`. Для магнита в ней ещё `datasets`, `layout`, `plan` и `issues` — расхождения магнита (IMP-16).

**Строка плана:** `{row, action, record_id, cells, changes, reason, message, decision}`.
- `cells` — значения сопоставленных столбцов, как в книге. `changes` — `{ключ: [было, станет]}`.
- Спорная строка (`conflict`):
  - `reason: "version_conflict"` — запись изменили после выгрузки шаблона;
  - `reason: "key_duplicate"` — ключ или запись уже встретились выше в книге.
  По умолчанию спорная строка пропускается. `decision: "apply"` разрешён только для `version_conflict`, иначе `400 import_decision`.
- Строка с ошибкой (`error`) не применяется; `reason` — код ошибки значения.

**План точен.** Все строки выполняются той же логикой, что и при применении, в части транзакции, которая затем откатывается. Поэтому уникальные поля, справочники, ККС и повторы внутри книги проверены заранее.

**Применение** — одна транзакция (IMP-05).
- **Устаревший план не применяется** (IMP-04), ответ — `409 import_stale` и ничего не записывается, если:
  - запись из плана изменилась или исчезла;
  - ключ занят новой записью;
  - изменилась схема типа;
  - для магнита — изменились целевые реестры, структура или правило кода, либо итог разошёлся с планом.
- Ошибка строки при применении — `409 import_failed` с номером строки, ничего не записано.
- Повтор применённого пакета возвращает прежний отчёт (IMP-06). Повтор той же книги новым пакетом даёт строки «без изменений» и не создаёт версий.
- **Отчёт:** `{counts, skipped: [{row, reason, message}], dataset_id, type_id}`, для магнита — `{counts, datasets, result}`. С `save_profile` сохраняется профиль: профиль с тем же названием заменяется. После применения книга и строки плана удаляются, отчёт остаётся в пакете.
- **Ошибки загрузки:**
  - не `.xlsx` — `400 import_file_name`;
  - не книга — `400 xlsx_invalid`;
  - превышены пределы IMP-11 — `400 xlsx_too_large`, `xlsx_too_many_sheets`, `xlsx_too_wide`, `xlsx_too_many_rows`;
  - истёк срок — `409 import_expired`.
- **Разбор книги идёт вне транзакции записи** (API-07): загрузка, план и применение — маршруты без ключа идемпотентности, их повтор безопасен сам по себе. Проверка строк плана держит запись базы на время проверки: 5000 строк — 2–5 с.
- **Журнал:** `import.upload`, `import.apply` (в `details` — счётчики), `import.profile`, `import.profile_delete`.

## Документы

Документы, их чтение и поиск по ним (ТЗ 8, KNOW-01…04, DATA-09).

- **Права.** Документ видят роли с правом `view` на его тип (`doc_type` в матрице прав: UUID типа или `*`). Без права документ не существует — ответ `404`. Загрузка, замена, архив, привязки и решения по упоминаниям — раздел `documents`; его получили роли «Администратор» и «Инженер».
- **Стартовые типы** — «Документ» (по умолчанию) и «Схема».

| Метод и путь | Тело запроса | Ответ |
| --- | --- | --- |
| `GET /document-types` | — | `{items: [{id, name}]}` — видимые типы |
| `POST /documents?name=&title=&type_id=` | файл как есть, до 100 МиБ | документ, `201` |
| `GET /documents?target_kind=&target_id=&state=&archived=&limit=` | — | `{items, more}` |
| `GET /documents/{id}` | — | документ |
| `GET /documents/{id}/file` | — | файл текущей версии |
| `PUT /documents/{id}/file?name=&version=` | файл | документ: новая версия или прежняя, если файл тот же |
| `GET /documents/{id}/text?page=` | — | `{version, items: [{ordinal, page, area, text}]}` — фрагменты |
| `POST /documents/{id}/archive` | — | документ |
| `POST /documents/{id}/links` | `{kind: "record" \| "kks", id}` | документ |
| `DELETE /documents/{id}/links/{kind}/{target}` | — | документ |
| `GET /documents/{id}/mentions` | — | `{items: [{kks_id, code, site_id, pages, hits, state}]}` |
| `POST /documents/{id}/mentions/{kks_id}` | `{decision: "confirm" \| "reject"}` | упоминания |

- **Документ:** `{id, title, type: {id, name}, version, state, pages, file_name, file: {name, sha256, size, media_type}, error, reader, read_at, created_by, links, job, can: {edit}, created_at, updated_at, archived}`.
- **Чтение** (KNOW-01). `state`: `queued` — в очереди, `reading` — читается, `ready` — готово, `empty` — текста нет (например, скан до распознавания), `error` — ошибка после трёх попыток, текст в `error`.
  - `reader` — кто читает: `server` — сам сервер (`.txt`, `.md`, `.csv`, `.xlsx`, `.docx`); `vision` — процесс схем (`.pdf`, `.dxf`, `.png`, `.jpg`, `.tif`, `.bmp`).
  - Другой формат — `400 document_format`.
  - `job` — незавершённая задача чтения `{state, attempts}` или `null`.
- **Файл** хранится один раз по SHA-256 (DATA-09). Загрузка и замена — маршруты без ключа идемпотентности: повтор того же файла ничего не дублирует.
- **Замена** (KNOW-04) — с текущей `version`, иначе `409 version_conflict`. Тот же файл ничего не меняет. Новый файл:
  - даёт новую версию;
  - сразу убирает прежние фрагменты из поиска;
  - ставит чтение заново и отменяет незавершённое чтение прежней версии.
- **Архив** убирает фрагменты из поиска и отменяет чтение.
- **Фрагменты** (KNOW-02) — абзацы до 1200 знаков с перекрытием 150 знаков, страница внутри фрагмента не смешивается. `page` — номер страницы, имя листа книги или страница, которую назвал процесс схем; `area` — область на листе, если её передал читатель. Векторный индекс добавится, когда будет выбрано расширение SQLite (ТЗ 4.2).
- **Привязки.**
  - Привязать к записи можно, только если её реестр виден, иначе `404`.
  - В карточке документа привязка к записи без права на реестр показана как `{kind: "record", id, access: false}` — «нет доступа».
  - Документы записи или ККС: `GET /documents?target_kind=record&target_id=…`.
- **Упоминания** (KNOW-03). Коды ККС и коды сигналов, найденные в тексте и известные каталогу, становятся предложениями (`state: "proposed"`) со страницами и числом вхождений. Связь «документ ↔ ККС» появляется только после `confirm`. Отклонённое и подтверждённое при новом чтении сохраняются, предложения пересчитываются.
- **Поиск.** `GET /search` возвращает `documents: [{document_id, title, type, page, snippet}]` — по одной лучшей странице документа, только видимых типов и текущих версий.
- **Журнал:** `document.create`, `document.replace`, `document.read`, `document.archive`, `document.link`, `document.unlink`, `document.mention`.

| `DELETE /knowledge/glossary/{id}` | — | — |

- **Заметка:** `{id, title, body, state, origin, version, scope, sources, author, confirmed_by, confirmed_at, stale_reason, reject_reason, created_at, updated_at}`.
  - `scope` — на что заметка: `{kind: "kks", id, code}`, `{kind: "type", id, name}` или `{kind: "station"}`.
  - `origin` — `user` или `ai`: ИИ предлагает заметку от имени пользователя.
- **Состояния** (KNOW-06): `proposed` → `confirmed` → `stale` или `rejected`. `GET /knowledge/notes` и общий поиск по умолчанию отдают только подтверждённые: на них опирается ИИ. Другие состояния — `state=proposed,stale`.
- **Источники** (KNOW-07): `{kind, id, version, page, current_version, …}`.
  - `version` — версия записи или документа на момент подтверждения. Подтверждение фиксирует текущие версии заново.
  - Источник, которого нет или который автор не видит, — `400 note_source_missing`.
- **Устаревание** (KNOW-08) делает сама база: правка, архив и удаление записи-источника, замена и архив документа-источника переводят предложенную и подтверждённую заметку в `stale` с причиной в `stale_reason`. В журнал и в события пишется `note.stale` — любым путём изменения: правкой, импортом, пакетной правкой.
- **Подтверждение устаревшей** — «проверено, верно». Если источник удалён, подтвердить нельзя (`note_source_missing`): сначала исправьте источники.
- **Правка** возвращает заметку в `proposed` и требует нового подтверждения. Править может автор или роль со «Знаниями»; нужна текущая `version`, иначе `409 version_conflict`. Отклонённую заметку перед подтверждением нужно исправить (`409 note_rejected`).
- **Права** (SEC-06): заметку видит только тот, кто видит все её источники — запись по праву на реестр, документ по праву на тип. Иначе `404`; в списках и в поиске заметки нет.
- **Словарь** (KNOW-10): `term` — местное название, уникальное без учёта регистра и пробелов, иначе `409 term_taken`; `kks_ids` — объекты ККС, которые оно означает.
  - Общий поиск находит термин и как всю строку, и как слово в ней. Он возвращает `glossary`, ставит объекты термина первыми (`via: "glossary"`, `term`) и добавляет записи с их кодами.
- **Журнал:** `note.propose`, `note.edit`, `note.confirm`, `note.reject`, `note.stale`, `glossary.add`, `glossary.update`, `glossary.delete`.
- Оценки ответов ИИ (KNOW-05) и диалоги (KNOW-12) — в разделе «ИИ».

## Фоновые задачи

Очередь задач (VIS-01, VIS-02). Задачи `document.read` с `reader: "vision"` выполняет процесс схем. Он входит служебной учётной записью с разделом `worker` («Фоновые задачи: выполнять»). Сервер свои задачи (`reader: "server"`) выполняет сам фоновым потоком.

| Метод и путь | Тело запроса | Ответ |
| --- | --- | --- |
| `GET /jobs?state=` | — | `{items}` — администратору и исполнителю |
| `POST /jobs/claim` | `{reader?: "vision", kinds?}` | `{job, document}` или `{job: null}` |
| `POST /jobs/{id}/complete` | `{pages: [{page?, text, area?}]}` | `{job, result: {state, pages, chunks, mentions}}` |
| `POST /jobs/{id}/fail` | `{error, retry?: true}` | `{job}` |

- **Захват.** Берётся старейшая задача — из очереди или с истёкшей арендой. Аренда — 10 минут; исполнитель — логин учётной записи.
  - `document` в ответе: `{id, version, file_name, sha256, media_type, file_url}`; файл скачивается по `file_url` той же учётной записью.
  - Документ переходит в `reading`. Если очередь пуста — `{job: null}`; процесс опрашивает её раз в несколько секунд.
- **Результат** — постраничный текст.
  - Сервер делит его на фрагменты, индексирует и находит коды ККС. До 20 млн знаков; тело запроса — до 64 МиБ.
  - Чужая или отменённая задача — `409 job_not_held`.
  - Документ заменили во время чтения — задача закрывается, а текст не сохраняется (`result.state: "stale"`).
- **Неудача.** С `retry: true` задача возвращается в очередь, пока есть попытки (три). После последней неудачи задача и документ получают `error`; текст ошибки виден пользователю.
- Задачи прежней версии документа отменяются при замене файла и при архиве.

## Общий поиск

| Метод и путь | Ответ |
| --- | --- |
| `GET /search?q=&limit=&site_id=` | `{query, kks, records, more: {records}, documents, notes, glossary, took_ms}` |

Строка Ctrl+K в оболочке (ТЗ 5.1, 11.1). Право — `session`. `limit` — от 1 до 50, по умолчанию 20; `site_id` сужает поиск до площадки.

- **`kks`** — объекты каталога `{id, code, name, site_id, site, archived, exact, via?, signal?}`.
  - Первым идёт точное совпадение кода, псевдонима (`via: "alias"`) или кода сигнала по правилу станции (`via: "signal"`, `signal: "XQ01"`, AI-16).
  - Затем коды и псевдонимы, содержащие строку.
- **`records`** — записи всех реестров, которые пользователь видит, кроме архивных: `{id, dataset_id, dataset, label, version, match: {field, text}}`.
  - Слова строки ищутся как подстроки во всех полях. Первыми идут записи, где строка совпала с ключом (уникальным полем), затем новые.
  - `label` — подпись записи, как у ссылок; `match` — поле, в котором найдено.
  - Слова короче трёх знаков не ищутся в записях: строка из одного-двух знаков даёт только подсказки ККС.
- **Права** (ROLE-03):
  - реестр без права `view` не участвует;
  - в реестре со скрытыми от роли полями поиск идёт перебором видимых значений, поэтому совпадение по скрытому полю не выдаёт запись.
- `documents` — страницы прочитанных документов видимых типов (см. «Документы»).
- `notes` — подтверждённые заметки знаний, видимые пользователю: `{id, title, scope, snippet}`.
- `glossary` — термины словаря станции в строке; их объекты ККС идут первыми в `kks` с `via: "glossary"`, записи с их кодами — в `records` с `via: "glossary"` (см. «Знания»).
- **Ошибки:** пустая строка — `400 search_empty`, длиннее 200 знаков — `400 search_too_long`.
- **Скорость:** на 100 000 записях в пяти реестрах — от 1 до 25 мс; перебор реестра на 20 000 записей со скрытым полем — до 41 мс (PERF-07 — 300 мс).

## Выгрузка

| Метод и путь | Тело запроса | Ответ |
| --- | --- | --- |
| `POST /datasets/{id}/export` | `{format?, query?, sort?, columns?, headers?, group_by?, template?}` | файл |

Право — `dataset.export` вместе с `view` на реестр. Ответ — файл с `content-disposition: attachment` и именем «<реестр> <дата>.<формат>».

- `format` — `xlsx` (по умолчанию), `csv` или `json` (EXP-01, EXP-08).
- `query` — условия, как у `…/records/count` (`where`, `search`, `archived`, `kks`), `sort` — как у `…/records/query`: выгружаются ровно те записи, что видны в таблице.
- `columns` — ключи полей в нужном порядке, по умолчанию все видимые поля. Скрытое от роли поле не выгружается и не указывается: `400 export_columns` (EXP-04). `headers` — свои заголовки `{ключ: заголовок}` (EXP-03).
- **`template`** (по умолчанию `true`) — выгрузка для правки (EXP-02): первые столбцы «UUID» и «Версия» скрыты. Мастер импорта узнаёт их сам: по UUID обновляется та же запись, а правка записи после выгрузки показывается спорной строкой. Повторная загрузка неизменённой выгрузки не создаёт версий.
- **Значения** — так, как их читает импорт: справочник — названием, ККС — кодом, ссылка на запись — ключом цели (UUID, если у типа-цели нет уникального поля), несколько значений — через «; », дата — датой Excel, логическое — `ИСТИНА`/`ЛОЖЬ` в книге и «да»/«нет» в CSV.
- **Формулы** (EXP-05): текст, начинающийся с `=`, `+`, `-`, `@`, в книге — текстовая ячейка, в CSV — с апострофом впереди.
- **CSV** — UTF-8 с BOM, разделитель «;»: так его открывает Excel с русскими настройками.
- **`group_by`** (UI-14, AT-42) — ключ поля с одним значением из `columns`, например ККС объекта. Строки идут по полю группы, а значения, общие для всех строк группы, выводятся объединёнными ячейками; UUID и версия не объединяются. Мастер импорта заполняет объединённые ячейки обратно (IMP-17), поэтому такая выгрузка тоже загружается без лишних версий. Группировка — только для `xlsx`.
- **Пределы:** без группировки — до 100 000 строк, книга пишется потоком (100 000 строк — около 7 с); с группировкой — до 20 000 строк (около 5 с). Больше — `400 export_too_large`.
- Выгрузка читает базу одним снимком и не держит запись других пользователей.

## Общий чат

Один общий канал для всех пользователей базы (ТЗ 11.3). Сообщения хранятся в базе LOCALAI, внешних служб нет. Миграция `0008` выдала разделы `chat` и `chat_write` всем ролям, что были в базе, а `chat_moderate` — ролям с разделом «Администрирование».

| Метод и путь | Тело запроса | Ответ |
| --- | --- | --- |
| `GET /chat/messages?before=&after=&limit=` | — | `{items, more, first, last, last_read, unread}` |
| `POST /chat/messages` | `{text}` | сообщение, `201` |
| `PATCH /chat/messages/{id}` | `{text, version}` | сообщение |
| `DELETE /chat/messages/{id}?version=` | — | сообщение с `state: "deleted"` |
| `POST /chat/messages/{id}/hide` | `{reason?}` | сообщение с `state: "hidden"` |
| `POST /chat/messages/{id}/unhide` | — | сообщение |
| `GET /chat/messages/{id}/history` | — | `{items: [{version, text, at}]}` — от первого текста до текущего |
| `GET /chat/search?q=&limit=` | — | `{items}` — новые сначала |
| `POST /chat/read` | `{seq}` | `{last_read, unread}` |

- **Лента.** Без курсора — последние `limit` сообщений (по умолчанию 50, до 200), `before` — более ранние, `after` — новые после известного, то есть догрузка после потери связи. Сообщения в ответе идут по возрастанию `seq`; `more` — есть ещё в ту же сторону.
- **Сообщение:** `{id, seq, author: {id, name}, created_at, edited_at, version, state, text, refs, mine, can: {edit, delete, hide, unhide, history}}`.
  - `state` — `active`, `deleted` (удалено автором) или `hidden` (скрыто модератором; тогда есть `hidden: {at, by, reason}`).
  - У удалённого и скрытого `text: null` и пустые `refs`; модератор видит текст.
- **Текст** — от 1 до 4000 знаков, без управляющих символов, кроме перевода строки и табуляции. Не больше 30 сообщений в минуту от учётной записи, иначе `429 chat_rate_limit`.
- **Правка и удаление.** Править и удалять можно только своё действующее сообщение с текущей `version`:
  - чужое — `403 chat_not_author`;
  - удалённое или скрытое — `409 chat_message_closed`;
  - устаревшая версия — `409 version_conflict`.
  Прежний текст остаётся в истории. Историю видят автор и модератор, остальным — `403 chat_history_forbidden`.
- **Ссылки** (`refs`) разбираются при каждом чтении с правами читающего: `{kind, start, end, …}` — место в тексте.
  - `kks` — код ККС или код сигнала из текста, найденный в каталоге: `{id, code, site_id, signal, access: true}`.
  - `record` — разметка `[[record:UUID]]`: `{id, access, dataset_id?, dataset?}`. Без права на реестр и для несуществующей записи ответ одинаков: `access: false`, интерфейс пишет «нет доступа». Содержимое записи в ответ не попадает.
  - `document` — разметка `[[document:UUID]]`; до этапа 4 всегда `access: false`.
- **Непрочитанное.** `unread` — чужие действующие сообщения после отметки `last_read`. `POST /chat/read` двигает отметку только вперёд.
- **Журнал.** Действия пишутся в журнал: `chat.post`, `chat.edit`, `chat.delete`, `chat.hide`, `chat.unhide` (`entity_kind: "chat_message"`); текст сообщения в журнал не пишется.
- ИИ общий чат не читает (CHAT-09).

## События

Изменения, которые видит пользователь, для обновления открытых экранов без перезагрузки (API-09, UI-06, CHAT-02).

| Метод и путь | Ответ |
| --- | --- |
| `GET /events?after=&wait=` | `{cursor, events, more}` |

- Без `after` ответ — `{cursor, events: [], more: false}`: с этого `cursor` клиент начинает слушать.
- С `after` — события после него: `{cursor, events, more}`. Следующий запрос идёт с полученным `cursor`; при `more: true` — сразу.
- `wait` — сколько секунд ждать, если событий пока нет (0–25, по умолчанию 0). Ответ приходит сразу после записи, которая дала видимое событие, или по истечении `wait` с пустым `events`. Запись из другого процесса, например переноса из командной строки, замечается не позже чем через секунду.
- Событие: `{seq, at, action, kind, id, dataset_id, actor}`. Данных изменения в событии нет: клиент читает их обычными маршрутами со своими правами.
- **Видимость:**
  - записи и реестры — с правом `view` на реестр;
  - сообщения чата — с разделом `chat`;
  - документы — с правом `view` на их тип;
  - заметки знаний — тому, кто видит все их источники;
  - черновики изменений от ИИ — только тому, кто задал вопрос;
  - ККС, поля, типы, площадки, справочники — каждому вошедшему;
  - остальное — роли с разделом «Администрирование».
  Журнал, перенесённый из Local_DB, событий не даёт.
- Источник событий — журнал аудита. `cursor` — номер его строки, поэтому пропущенное после потери связи догружается по курсору.

## ИИ

Вопросы к ИИ, диалоги, оценки ответов и черновики изменений (ТЗ 9). Все маршруты — раздел `ai` («ИИ»); настройки и выгрузка оценок — «Администрирование».

ИИ-служба — отдельный процесс на этом компьютере (`python -m ai`). Интерфейс разговаривает только с сервером; сервер передаёт вопрос службе вместе с **делегированным доступом** — токеном `ai.…` от имени спросившего (API-10). С ним служба читает данные через этот же API и видит ровно то, что видит пользователь.

| Метод и путь | Тело запроса | Ответ |
| --- | --- | --- |
| `GET /ai/status` | — | `{service, model, fallback, cloud_allowed, limits: {steps, calls}}`; модель — `{provider, name, configured, available, remote}` или `null` |
| `GET /ai/schema` | — | `{sites, datasets: [{id, name, site_id, site, type, can_edit, fields}]}` — что пользователь может спрашивать |
| `GET /ai/dialogs?limit=` | — | `{items: [{id, title, created_at, updated_at, messages}]}` — свои, свежие сначала |
| `POST /ai/dialogs` | `{title?}` | диалог, `201` |
| `GET /ai/dialogs/{id}` | — | диалог с `messages` |
| `PATCH /ai/dialogs/{id}` | `{title}` | диалог |
| `DELETE /ai/dialogs/{id}` | — | — |
| `POST /ai/dialogs/{id}/messages` | `{text, context?: {dataset_id?, record_ids?, kks_id?, document_id?}}` | поток NDJSON, см. ниже |
| `PUT /ai/messages/{id}/feedback` | `{verdict: "right" \| "wrong", correction?}` | `{message_id, verdict, correction}` |
| `GET /ai/feedback` | — | `{items: [{question, answer, verdict, correction, sources, at}]}` — «Администрирование» |
| `GET /ai/drafts?state=&limit=` | — | `{items}` — свои черновики |
| `POST /ai/drafts` | `{kind, summary, payload}` | черновик, `201` — только ИИ-служба |
| `GET /ai/drafts/{id}` | — | черновик |
| `POST /ai/drafts/{id}/accept` | — | черновик |
| `POST /ai/drafts/{id}/reject` | `{reason?}` | черновик |
| `GET /ai/settings` | — | `{retention_days, cloud_allowed, model, fallback}` — «Администрирование» |
| `PUT /ai/settings` | `{retention_days?, cloud_allowed?, confirm_cloud?, model?, fallback?}` | настройки — «Администрирование» |

- **Вопрос** — поток строк JSON (`application/x-ndjson`, AI-11). Ключ идемпотентности не нужен. Строки:
  - `{type: "question", message}` — сохранённый вопрос, первая строка;
  - `{type: "thinking"}` — модель размышляет перед шагом (если размышление включено);
  - `{type: "tool", name, args}` — выполняется инструмент;
  - `{type: "text", delta}` — кусок ответа;
  - `{type: "draft", draft}` — ИИ создал черновик изменения;
  - `{type: "message", message}` — сохранённый ответ, последняя строка.
- **Сообщение:** `{id, dialog_id, role, text, status, path, model, context, steps, sources, took_ms, created_at, feedback}`; `model` — какая модель ответила.
  - `status`: `done`; `limit` — ответ прерван пределом (AI-10); `no_model` — модели нет или облачная не разрешена, ответ без неё (AI-12); `no_service` — служба ИИ недоступна; `error` — служба или модель оборвали ответ.
  - `path`: `fast` — точный вопрос без модели (AI-03), `model` — с моделью, `null` — ни то ни другое.
  - `steps` — `[{tool, args}]`: какие инструменты выполнялись.
  - `sources` (AI-07) — `[{n, kind, id, label, …}]`; `[n]` в тексте ссылается на источник с этим номером. `kind`: `kks`, `record` (`dataset_id`), `document` (`page`), `note`, `dataset` (`filter` — запрос подсчёта: тот же фильтр открывает таблицу, AT-26; `group_by` — поле группировки).
  - `feedback` — `{verdict, correction}` или `null`.
- **Без модели** (AI-03, AI-12) отвечаются: код ККС или псевдоним — карточка; код сигнала — строка сигнала (шкаф, клеммник, клеммы, кабель); «сколько …» с названием реестра — подсчёт с условиями по значениям справочников и коду ККС. Если модель доступна, без неё отвечается только вопрос, в котором правила поняли каждое слово.
- **Делегированный доступ:**
  - только читает (AI-09): изменяющий маршрут отвечает `403 ai_read_only`, кроме `POST /ai/drafts`;
  - не больше 24 обращений за ответ (`429 ai_call_limit`), не дольше 5 минут; после ответа отзывается (`401 ai_grant_invalid`);
  - заблокированный пользователь теряет его сразу (`401 session_invalid`).
- **Черновики** (AI-09, AT-33): `kind` — `record_edit` (`payload: {record_id, values}`) или `note` (`payload: {title, body, scope?, sources?}`).
  - При создании проверяются права спросившего: видеть и править реестр, править поля. Запись хранится с `before` — значениями до правки — и `target_version`.
  - Принять может только спросивший. Правка выполняется от его имени и с его правами: в журнале записи автор — человек. Если запись изменилась после предложения — `409 version_conflict`, черновик остаётся предложенным. Принятая заметка становится заметкой знаний в состоянии `proposed` с `origin: "ai"`.
  - Принятый или отклонённый черновик повторно не решается: `409 ai_draft_decided`.
  - ИИ получает инструмент `propose`, только если сам вопрос просит изменить данные: текст документов и записей включить его не может (AT-40).
- **Диалоги** видит и удаляет только владелец; чужой диалог, сообщение и черновик — `404`, в том числе для администратора. Срок хранения — `retention_days` (1–3650, по умолчанию 180, KNOW-12).
- **Оценка** (KNOW-05) хранится с вопросом, ответом и источниками и переживает удаление диалога.
- **Модель** (AI-01) — настройка, а не код. `model` — основная, `fallback` — запасная: она отвечает, если основная не установлена, не запущена или отказала до первого слова. `null` — модель, с которой запущена служба. Настройка модели:
  - `provider` — `ollama` (по умолчанию) или `openai`: OpenAI-совместимый сервер (llama.cpp, vLLM, LM Studio);
  - `url` — адрес, по умолчанию `http://127.0.0.1:11434`;
  - `name` — имя модели; пусто — служба сама берёт самую крупную установленную модель, умеющую вызывать инструменты;
  - `think` — размышление: `auto` (как решит модель), `off`, `on`, `low`, `medium`, `high`;
  - `context` — окно контекста в токенах, 2048–262144, по умолчанию 32768. У Ollama окно по умолчанию мало для схемы реестров и результатов инструментов;
  - `temperature` — 0–2, по умолчанию 0,2;
  - `api_key` — ключ доступа, если сервер модели его требует. Наружу не отдаётся: в ответе вместо него `api_key_set`. `null` или отсутствие ключа при том же `url` сохраняет прежний.
  Неверная настройка — `400 ai_model_invalid`. Смена модели действует со следующего вопроса, без перезапуска службы.
- **Список моделей** — что установлено у поставщика, с умениями (`tools`, `thinking`, `vision`) и размером; `auto` — какую модель служба выберет сама.
- **Проверка модели** — вопрос станции по-русски с инструментом `kks_card` и вымышленным результатом. `checks`:
  - `tool_call` — вызвала инструмент с правильным кодом;
  - `uses_result` — взяла число из результата;
  - `cites` — поставила ссылку `[n]`;
  - `russian` — ответила по-русски.
  `score` — сколько проверок пройдено из 4. Без службы ИИ — `503 ai_unavailable`.
- **Облачная модель** (AI-15) выключена. Модель на другом компьютере работает только при `cloud_allowed: true`; включение требует `confirm_cloud: true`, иначе `400 ai_cloud_confirm_required`.
- **Журнал:** `ai.draft_propose`, `ai.draft_accept`, `ai.draft_reject`, `ai.settings`. Вопросы и ответы в журнал не пишутся: это переписка пользователя.

### ИИ-служба

Служба слушает только этот компьютер и принимает запросы только с заголовком `X-LocalAI-Key` — ключом из файла `ai.key` рядом с базой; сервер создаёт его при первом запуске (SEC-05). Сервер ищет службу по `--ai-url` или `LOCALAI_AI_URL`, по умолчанию `http://127.0.0.1:8731`.

| Путь службы (не API сервера) | Метод | Ответ |
| --- | --- | --- |
| `/health` | `GET`, `POST {models}` | `{service: "ai", model, fallback}` |
| `/ask` | `POST` | поток NDJSON: `thinking`, `tool`, `text`, `draft`, последней — `{type: "done", status, path, model, steps, sources, calls, took_ms}` |
| `/models` | `POST {config}` | `{items, auto}` |
| `/check` | `POST {config}` | результат проверки модели |

Тело `/ask` от сервера: `{question, context, history, token, cloud_allowed, models: {primary, fallback}, limits: {steps, calls}}`.

## Журнал и состояние

| Метод и путь | Ответ |
| --- | --- |
| `GET /audit?entity_id=&dataset_id=&before=&limit=` | события от новых к старым; `before` — `seq` последнего события предыдущей страницы |
| `GET /system/allowed-ips` | разрешённые сети: `{id, network, note, created_at}` |
| `POST /system/allowed-ips` | `{network, note?}` — адрес `10.0.5.7` или сеть `10.0.5.0/24`; ответ — запись списка, `201` |
| `DELETE /system/allowed-ips/{id}` | — |
| `GET /system/health` | `{"status": "ok", "version": "0.1.0", "schema_version": 4, "database_id": "…", "setup_required": false}`; `setup_required` — в базе ещё нет ни одного пользователя |

Разрешённые адреса (SEC-04) — `section.admin`. Пустой список пропускает любой адрес; непустой — только адреса из своих сетей, остальным любой маршрут, в том числе вход, отвечает `403 address_not_allowed`. Адрес самого сервера (`127.0.0.1`, `::1`) пропускается всегда. Изменение, после которого адрес администратора, сделавшего его, окажется вне списка, отклоняется — `409 network_lockout`.

**HTTPS** (SEC-04). По умолчанию сервер слушает только `127.0.0.1`. В сети он запускается только с сертификатом: `python -m server.admin --db … create-certificate --host <имя> --host <адрес>` создаёт ключ и самоподписанный сертификат в папке `tls` рядом с базой и печатает отпечаток SHA-256 для сверки в браузере. Без сертификата `python -m server --host 0.0.0.0` не запускается. По HTTPS cookie сессии получает признак `Secure`.

Событие журнала: `{seq, at, actor_id, actor_label, origin, action, entity_kind, entity_id, dataset_id, details}`. `action` имеет вид `record.update`, `kks.rename`, `field.create`. События доступа: `auth.login`, `auth.login_failed` (в `details` — введённый логин и причина), `auth.logout`, `user.create`, `user.update`, `user.block`, `user.unblock`, `user.password_reset`, `user.password_change`, `role.create`, `role.update`, `role.archive`, `role.restore`, `role.permissions` (в `details` — добавленные и снятые права), `backup.create`, `backup.restore`, `network.allow`, `network.remove`. `actor_id` — UUID учётной записи (ROLE-04).
