# ТЗ LOCALAI 1.0: единая инженерная база с ИИ

Редакция от 17.11.2026. Это копия ТЗ для исполнителей; исходный документ с двумя диаграммами ведёт владелец. Изменения в ТЗ вносятся только по решению владельца.

## 1. Назначение, цели и границы

LOCALAI — единый продукт в одном репозитории: локальная инженерная база с каталогом ККС и встроенным ИИ. Он заменяет Local\_DB, Core и Visual и сохраняет все их функции.

Это ТЗ — проект для согласования. Оно собрано из двух аудитов, ТЗ «KKS Excel Import v1.0» и требований владельца от 15.11.2026. Допущения, принятые без подтверждения, собраны в разделе 19.

### 1.1 Цели версии 1.0

| Код | Цель | Как проверяется |
| --- | --- | --- |
| Ц1 | База гибкая: новый тип данных создаётся без программиста | Тип создан из Excel на 1000 строк мастером импорта |
| Ц2 | База быстрая и компактная | Цели раздела 13 выполнены на копии рабочей базы |

| Ц5 | ИИ гибкий | Новый реестр доступен в чате без изменения кода; модель меняется настройкой |

### 1.2 Что не входит в версию 1.0

- Дообучение модели на данных станции: ИИ становится полезнее за счёт знаний в базе, веса модели не меняются.
- Автономная запись ИИ в базу: ИИ готовит предложения, записывает человек.
- Облачные модели по умолчанию: подключение возможно только отдельным решением администратора.
- Сервер СУБД, репликация между площадками, мобильное приложение.
- Доказательные этапы восстановления линии E5 из Local\_DB.

## 2. Термины и принципы

Двенадцать терминов и восемь принципов ниже обязательны для всех разделов; любое отступление оформляется как изменение ТЗ.

### 2.1 Термины

| Термин | Значение |
| --- | --- |
| Тип | Описание вида данных: набор полей, их типы и правила. Примеры: оборудование, кабель, муфта |
| Реестр | Рабочий набор записей одного типа на одной площадке. Заменяет режимы «Эксплуатация» и «Кабели» |
| Площадка | Станция или объект, в пределах которого код ККС уникален |
| Запись | Строка реестра с UUID, версией и историей |
| Объект ККС | Физический объект с постоянным UUID; код и псевдонимы могут меняться |
| Связь | Отношение записи к объекту ККС с ролью (объект, начало, конец, через, сигнал), позицией и, при необходимости, контактом |
| Код сигнала | ККС объекта и признак сигнала по стандарту KKS: `01MAJ81AA203XB01` — сигнал `XB01` объекта `01MAJ81AA203`. Сигнал — строка реестра сигналов, а не объект каталога |
| Магнит ККС | Правило импорта: каждая строка источника притягивается к объекту ККС, сколько бы строк ни ссылалось на один код |
| Ссылка на запись | Поле, которое хранит UUID записи другого реестра: сигнал → кабель, кабель → муфта |
| Граф объектов | Объекты ККС и записи как узлы, связи ККС и ссылки на записи как рёбра; из него строятся кабельная и логическая схемы и путь `trace` |
| Документ | Файл с типом и названием, привязанный к записям или объектам ККС |
| Лист | Страница документа или чертеж с распознанными элементами и соединениями |
| Фрагмент | Часть текста документа с адресом: документ, лист, область. Единица поиска для ИИ |
| Заметка знаний | Утверждение с источником, автором и состоянием, накопленное в ходе работы с ИИ |
| Профиль | Сохранённые правила разбора или выгрузки Excel для одного реестра |
| Роль | Именованный набор прав; хранится как данные, переименовывается без потери прав |

### 2.2 Принципы

1. **Один владелец.** У каждой операции один обработчик, у каждого экрана один модуль, у чтения данных один слой запросов.
2. **Связи по ID.** Названия типов, реестров, ролей и коды ККС только отображаются; переименование ничего не ломает.
3. **Права проверяет сервер.** Неизвестный маршрут, роль или ресурс получает отказ. Скрытая кнопка защитой не считается.
4. **Одно действие — одна транзакция.** Изменение либо записано целиком вместе с аудитом, либо не записано совсем.
5. **ИИ читает и предлагает.** Запись в базу выполняет только человек, подтверждая предложение.
6. **У знания есть источник и состояние.** ИИ опирается только на данные базы, документы и подтверждённые заметки и показывает, на что именно.
7. **Замена, а не слой.** Новая реализация удаляет старую в том же изменении. Файлы-заплатки и версии в именах модулей запрещены.
8. **Принято по сценарию.** Требование выполнено, когда его приёмочный сценарий проходит на данных из рабочей базы.

## 3. Архитектура и репозиторий

LOCALAI — один репозиторий и четыре процесса: сервер, ИИ-служба, процесс схем и модель. В базу пишет только сервер; остальные работают через его API.

```
Интерфейс в браузере ──HTTPS──▶ Сервер LOCALAI ──▶ SQLite и файлы
                                 │  API v1 и права        ▲ пишет только сервер
                                 │  Очередь задач
ИИ-служба ──API v1, права пользователя──▶ Сервер
   └──▶ Модель (Ollama)
Процесс схем ──API v1──▶ Сервер
```

Сервер — единственный, кто пишет в базу; ИИ-служба и процесс схем работают через него.

Интерфейс обращается только к серверу; вопросы чата сервер передаёт ИИ-службе, а та получает данные обратно через API с правами спрашивающего. Остановка ИИ-службы, модели или процесса схем не мешает работе с данными.

| Компонент | Каталог | Технология | Отвечает за |
| --- | --- | --- | --- |
| Хранение | `engine/` | Python 3.13, SQLite в режиме WAL, FTS5 | Схема базы, миграции, слой запросов, транзакции |
| Сервер | `server/` | FastAPI | API v1, права, импорт и экспорт, файлы, копии, аудит, очередь задач |
| ИИ-служба | `ai/` | Python, адаптер модели | Инструменты, поиск, ответы, предложения, набор проверочных вопросов |
| Процесс схем | `vision/` | Python, библиотеки разбора PDF, DXF и распознавания | Чтение документов, листы, граф листа |
| Интерфейс | `web/` | TypeScript, фреймворк и Vite | Все экраны; собирается в статические файлы |
| Поставка | `packaging/` | Установщик Windows | Установка, обновление, панель управления |
| Проверки | `tests/`, `tools/` | pytest, сценарии в браузере | Тесты поведения, замеры, генератор данных |
| Документы | `docs/` | Markdown | Это ТЗ, контракт, реестр функций, состояние, правила |

Требования к репозиторию:

| Код | Требование |
| --- | --- |
| ARCH-01 | Пакет `engine` не импортирует `server`, `ai`, `vision`; направление зависимостей проверяется тестом |
| ARCH-02 | ИИ-служба и процесс схем не открывают файл базы; все данные они получают и отдают через API |
| ARCH-03 | Функция длиннее 150 строк и модуль длиннее 800 строк не проходят проверку стиля |
| ARCH-04 | Маршруты объявляются по модулям областей; обработчик получает сервисы через явные зависимости, а не из общего состояния |
| ARCH-05 | В именах модулей и файлов нет номеров версий, дат и слов «patch», «fix», «hotfix» |

Ограничения ARCH-03 и ARCH-04 введены по итогам аудита: в Core все маршруты лежали в одной функции на 1 716 строк, а в Local\_DB обработчики 243 раза обращались к общему состоянию приложения.

## 4. Модель данных

Все данные, знания ИИ и очередь задач лежат в одном файле SQLite; запись хранится как JSON-документ, а связи и ККС — как обычные таблицы с внешними ключами. Такое хранение в замере на 10 000 записей дало файл 26 МБ вместо 47,7 МБ и импорт 1000 записей за 43 мс.

### 4.1 Таблицы

| Группа | Таблицы | Назначение |
| --- | --- | --- |
| Структура | `sites`, `types`, `fields`, `datasets` | Площадки; типы и их поля с ревизией схемы; реестры |
| Записи | `records`, `record_versions` | Запись: UUID, реестр, версия, JSON-документ, признак архива. История хранит разницу между версиями |
| Справочники | `dictionaries`, `dictionary_values` | Закрытые списки значений с синонимами |
| ККС и связи | `kks_objects`, `kks_aliases`, `record_kks_links`, `record_links`, `kks_rules` | Каталог объектов, псевдонимы, связи записей с ККС и с другими записями (роль, позиция, контакт); правила кода станции |
| Файлы и документы | `files`, `documents`, `document_links` | Файл по SHA-256 без дублей; документ с типом; привязка к записям и ККС |
| Схемы | `sheets`, `sheet_elements`, `sheet_edges` | Листы, распознанные элементы с координатами, соединения между ними |
| Поиск | `record_fts`, `chunks`, `chunk_fts`, `chunk_vectors` | Полнотекстовый индекс записей; фрагменты документов с полнотекстовым и векторным индексом |
| Память ИИ | `knowledge_notes`, `glossary_terms`, `ai_dialogs`, `ai_messages`, `ai_feedback`, `ai_drafts` | Заметки знаний, словарь станции, диалоги, оценки ответов, предложения изменений |
| Доступ | `users`, `roles`, `role_permissions`, `sessions`, `allowed_ips` | Пользователи, роли как данные, матрица прав, сессии |
| Аудит | `audit_log` | Кто, что и когда изменил; записывается в той же транзакции |
| Обмен | `import_profiles`, `import_batches`, `import_rows`, `export_profiles` | Профили, пакеты импорта и строки плана на сервере |
| Фоновые задачи | `jobs` | Очередь индексации документов и разбора схем с состоянием и попытками |
| Переносимые модули | Проверки и акты, табель | Переносятся из Local\_DB со своей структурой |

### 4.2 Требования

| Код | Требование |
| --- | --- |
| DATA-01 | Новый тип, поле или реестр создаются через интерфейс и API без изменения кода и без миграции схемы базы |
| DATA-02 | При записи JSON-документ проверяется по схеме типа: типы значений, обязательность, справочники |
| DATA-03 | Для поля, отмеченного как фильтруемое или сортируемое, сервер сам создаёт индекс по выражению JSON |
| DATA-04 | Каждая запись имеет UUID и номер версии; запись с устаревшей версией отклоняется |
| DATA-05 | История хранит разницу между версиями; любая версия восстанавливается и откатывается |
| DATA-06 | Код ККС уникален в пределах площадки по нормализованному виду; переименование сохраняет UUID, старый код становится псевдонимом |
| DATA-07 | Связь записи с ККС хранит роль и позицию; повтор одной связи запрещён ограничением базы |
| DATA-08 | Реестры, ККС, связи, документы и права защищены внешними ключами; архив не удаляет связи |
| DATA-09 | Файл хранится один раз по SHA-256, сколько бы документов на него ни ссылалось |
| DATA-10 | База работает в режиме WAL с включёнными внешними ключами; клиенты обращаются к ней только через API |
| DATA-11 | Схема базы меняется только нумерованными миграциями; перед каждой создаётся проверенная резервная копия |
| DATA-12 | Поле может быть отмечено «уникальное в реестре». Повтор значения по нормализованному виду среди действующих записей реестра отклоняется; ответ называет запись, у которой значение уже есть |
| DATA-13 | Поле вида «ссылка на запись» хранит UUID записи из заданного реестра или типа. Ссылка на несуществующую запись отклоняется; переименование и архив целевой записи связь не рвут; карточка записи показывает и прямые, и обратные ссылки |
| DATA-14 | Связь с ККС и ссылка на запись могут хранить контакт: клемму, жилу, вход или выход блока. Контакт — текст рядом с ролью и позицией |
| DATA-15 | Связи ККС и ссылки на записи образуют граф объектов. Сервер отдаёт окрестность объекта на заданную глубину и путь между двумя объектами с учётом прав спрашивающего |
| DATA-16 | Правила кода ККС станции хранятся в базе и меняются без изменения кода: как из кода выделяются ККС объекта и признак сигнала. По умолчанию признак сигнала — `X`, латинская буква и две цифры в конце кода (`XQ01`, `XB62`). Одни и те же правила применяют импорт, поиск, карточка ККС и ИИ |

Векторный индекс требует расширения SQLite для поиска по векторам; конкретное расширение выбирается на этапе 4 по проверке на Windows.

## 5. Сервер и API

Сервер — единственный процесс, который пишет в базу; интерфейс, ИИ-служба и процесс схем работают через один API версии 1 с одними и теми же правами.

### 5.1 Группы маршрутов

| Группа | Назначение |
| --- | --- |
| `/api/v1/auth` | Вход, выход, смена своего пароля, текущая сессия и права |
| `/api/v1/users`, `/roles` | Пользователи, роли, матрица прав, сброс пароля |
| `/api/v1/types`, `/datasets` | Типы, поля, реестры, справочники |
| `/api/v1/datasets/{id}/records` | Страница записей, создание, правка, пакетная правка, архив, история, откат |
| `/api/v1/kks` | Поиск и разрешение кода, карточка ККС, псевдонимы, связи, трассировка |
| `/api/v1/documents`, `/files`, `/sheets` | Документы, файлы, листы схем, плитки для просмотра, элементы листа |
| `/api/v1/import`, `/export` | Профили, пакеты импорта, выгрузки |
| `/api/v1/search` | Единый поиск по записям, ККС, документам и заметкам |
| `/api/v1/knowledge` | Заметки знаний, словарь, очередь подтверждения |
| `/api/v1/ai` | Диалоги, сообщения, оценки, предложения изменений |
| `/api/v1/tools` | Карта эксплуатации, кабельная схема, ведомость ККС |
| `/api/v1/inspections`, `/timesheet` | Проверки и акты; табель |
| `/api/v1/backups`, `/audit`, `/jobs`, `/system` | Копии и восстановление, журнал, фоновые задачи, состояние |

### 5.2 Требования

| Код | Требование |
| --- | --- |
| API-01 | Один обработчик на метод и путь; автоматический тест отклоняет сборку с дублем |
| API-02 | Отказ по умолчанию: маршрут без явно объявленного права недоступен; открытые маршруты перечислены в одном списке |
| API-03 | Список, поиск, фильтр, сортировка и подсчёты выполняются в SQL одним слоем запросов; чтение всех записей в память запрещено |
| API-04 | Единый язык запросов: условия «поле, операция, значение», сортировка, курсор, размер страницы до 200. Им пользуются таблица, экспорт и ИИ |
| API-05 | Постраничный вывод по курсору; страница не зависит от общего числа записей |
| API-06 | Изменяющий запрос несёт ожидаемую версию записи и ключ идемпотентности; повтор возвращает прежний результат |
| API-07 | Транзакции записи короткие. Разбор Excel, индексация и разбор схем идут вне транзакции записи и не блокируют других пользователей |
| API-08 | Единый формат ошибки: код, понятный текст на русском, поле или строка, к которым она относится |
| API-09 | Сервер рассылает события об изменениях; открытые таблицы и карточки обновляются без перезагрузки |
| API-10 | ИИ-служба обращается к API от имени пользователя, задавшего вопрос, и получает ровно то, что разрешено ему |
| API-11 | Описание API формируется из кода и входит в репозиторий; расхождение описания и кода отклоняет сборку |

## 6. Импорт и экспорт

Обмен с Excel строится на одном мастере и на круговом обмене: выгруженный файл можно поправить и загрузить обратно, и записи обновятся, а не задвоятся. Разделы 7–11 ТЗ «KKS Excel Import v1.0» входят в это ТЗ целиком; ниже — их краткое изложение и дополнения.

### 6.1 Мастер импорта

1. **Файл.** Пользователь выбирает книгу `.xlsx` и листы; сервер показывает листы, предлагаемую строку заголовков и до 20 строк примера.
2. **Назначение.** Существующий реестр или новый тип («Создать тип и загрузить»).
3. **Сопоставление.** Подтвердить сохранённый профиль или связать столбцы с полями, выбрать ключ.
4. **Проверка.** Сводка: новые, изменённые, без изменений, спорные; фильтр по проблемам; решения по спорным строкам.
5. **Применение.** Все готовые строки записываются одной транзакцией.
6. **Отчёт.** Счётчики, номера листов и строк, причины пропусков; переход в реестр.

### 6.2 Требования к импорту

| Код | Требование |
| --- | --- |
| IMP-01 | Запись опознаётся по порядку: UUID из шаблона, затем внешний ID или подтверждённый бизнес-ключ реестра, иначе только добавление или ручное сопоставление |
| IMP-02 | Ключ не строится из номера строки или имени файла. Код ККС объекта ключом записи не служит: у объекта может быть много строк. Код сигнала или номер кабеля может быть подтверждённым бизнес-ключом реестра, если поле уникально (DATA-12) |
| IMP-03 | План импорта хранится на сервере; клиент не передаёт строки на применение |
| IMP-04 | Если между проверкой и применением изменились запись, схема или права, устаревший план не применяется |
| IMP-05 | Применение атомарно: сбой на любой строке не оставляет частичного результата |
| IMP-06 | Повтор того же запроса или той же книги не создаёт дублей и новых версий |
| IMP-07 | Пустая ячейка сохраняет текущее значение; отсутствие строки в Excel не архивирует запись |
| IMP-08 | Профиль сохраняет правила разбора и применяется к следующей книге того же вида без повторной настройки |
| IMP-09 | Строка может быть записью или точкой маршрута: 1000 строк с пятью точками на кабель дают 200 кабелей и 1000 связей |
| IMP-10 | Неизвестное обозначение ККС решается один раз и применяется ко всем строкам книги в пределах площадки |
| IMP-11 | Пределы первой версии: книга до 25 МиБ и 20 листов; лист до 5000 непустых строк и 200 столбцов; распакованные данные до 250 МиБ; обработка листа до 60 с. Превышение даёт понятную ошибку и не меняет базу |
| IMP-12 | Импорт доступен ролям с правом «импорт» на данный реестр; создание нового типа — только ролям с правом «структура» |
| IMP-13 | Магнит ККС: каждая строка источника притягивается к объекту ККС. Код разбирается по правилам станции (DATA-16); объект находится по нормализованному коду или псевдониму, иначе создаётся. Повтор кода в строках источника — норма и даёт один объект; код сигнала не создаёт объект каталога |
| IMP-14 | Мастер сам предлагает роль каждого столбца: ККС объекта, код сигнала, место (шкаф, коробка), номер кабеля, обычное значение. Основание — заголовок и доля значений, похожих на ККС. Предложение подтверждает человек; решение сохраняется в профиле |
| IMP-15 | Плоская таблица «строка на сигнал» раскладывается по реестрам: объект — в каталог ККС, сигналы — в реестр сигналов с ключом «код сигнала», кабели — в реестр кабелей с ключом «номер кабеля», сигнал ссылается на кабель (DATA-13). Общие для объекта значения не дублируются |
| IMP-16 | Расхождения не сливаются молча и выносятся в отчёт пробного прогона: код сигнала не начинается с кода объекта; повтор уникального значения; строка без ККС; разные данные одного объекта в реестре, где объект должен быть один. По умолчанию такие строки остаются при одном ККС и ждут решения человека |
| IMP-17 | Объединённые ячейки Excel заполняются значением верхней левой ячейки на весь диапазон |

### 6.3 Требования к экспорту

| Код | Требование |
| --- | --- |
| EXP-01 | Любой реестр или сохранённый вид с текущими фильтрами выгружается в `.xlsx` и CSV |
| EXP-02 | Выгрузка для правки содержит скрытые столбцы UUID и версии; обратная загрузка обновляет те же записи |
| EXP-03 | Профиль экспорта задаёт столбцы, порядок, заголовки и шаблон оформления |
| EXP-04 | Экспорт показывает только поля и записи, разрешённые пользователю |
| EXP-05 | Ячейки, которые Excel мог бы исполнить как формулу, экранируются |
| EXP-06 | Ведомость ККС, карта эксплуатации, кабельная схема и ответ ИИ выгружаются в файл |
| EXP-07 | Полный пакет содержит данные, файлы, права, знания ИИ и историю; он же служит резервной копией и способом переноса на другую машину |
| EXP-08 | Открытая выгрузка реестра в JSON для обмена с другими системами |

Трёхстороннее сравнение «прошлый импорт, база, Excel» из исходного ТЗ вводится вторым шагом: в версии 1.0 сравниваются база и Excel, каждое расхождение показывается пользователю.

## 7. Пользователи, роли и безопасность

Ролей сколько угодно, они хранятся как данные и переименовываются администратором; пароль принадлежит пользователю, а администратор может его сбросить.

### 7.1 Пользователи и роли

| Код | Требование |
| --- | --- |
| ROLE-01 | Администратор создаёт, переименовывает, копирует и отключает роли; число ролей не ограничено |
| ROLE-02 | Права привязаны к ID роли: переименование не меняет права, историю и журнал |
| ROLE-03 | Матрица прав роли: по реестру (видеть, создавать, править, архивировать, импорт, экспорт), по полю (видеть, править), по типу документа, по разделу (ИИ, инструменты, табель, копии, структура, администрирование) |
| ROLE-04 | У каждого человека своя учётная запись с логином и ролью; в журнал пишется учётная запись, а не введённое имя |
| ROLE-05 | Администратор создаёт пользователя, меняет его роль, блокирует и сбрасывает пароль на временный |
| ROLE-06 | После сброса пользователь обязан задать новый пароль при первом входе; действующие сессии закрываются |
| ROLE-07 | Пользователь сам меняет свой пароль; администратор пароли не видит |
| ROLE-08 | Последнего активного администратора нельзя отключить, удалить или лишить права администрирования |
| ROLE-09 | Изменение прав действует на уже открытые сессии не позже следующего запроса |
| ROLE-10 | При установке создаются стартовые роли «Администратор», «Инженер», «Наблюдатель»; все, кроме прав последнего администратора, изменяемо |

### 7.2 Защита

| Код | Требование |
| --- | --- |
| SEC-01 | Пароли хранятся как Argon2; токены сессий — только как хэш |
| SEC-02 | Сессия живёт не дольше 12 часов и закрывается после 15 минут простоя; попытки входа ограничены |
| SEC-03 | Установщик запускает сервер только в рабочем режиме; стартовых паролей в коде нет, пароль администратора от 12 символов задаётся при установке |
| SEC-04 | В сетевом режиме сервер работает по HTTPS с сертификатом, созданным при установке; список разрешённых IP остаётся дополнительной мерой |
| SEC-05 | ИИ-служба и процесс схем слушают только локальный адрес и принимают запросы только от сервера |
| SEC-06 | ИИ видит ровно то, что разрешено спрашивающему; заметка знаний наследует ограничения своих источников |
| SEC-07 | Текст документов для ИИ — данные, а не команды: указания внутри документа не меняют поведение ИИ и не дают права записи |
| SEC-08 | Все действия администратора, входы, импорты, экспорты и восстановления пишутся в журнал |
| SEC-09 | Резервные копии зашифрованы; восстановление сначала создаёт защитный снимок текущего состояния |
| SEC-10 | Внешних сетевых обращений нет: продукт полностью работает в закрытой сети |

Если владелец решит оставить один пароль на роль, требования ROLE-04 и ROLE-06 меняются, а журнал перестаёт доказывать, кто именно внёс изменение. Это решение вынесено в раздел 19.

## 8. Память ИИ: знания в базе

База служит памятью ИИ: в ней хранятся прочитанные документы, подтверждённый опыт и словарь станции. Модель при этом не дообучается — ИИ становится полезнее, потому что находит в базе больше проверенных знаний.

### 8.1 Три слоя памяти

| Слой | Что хранит | Как пополняется |
| --- | --- | --- |
| Знания из документов | Фрагменты текста с адресом «документ, лист, область»; упоминания ККС | Автоматически при привязке или замене документа |
| Опыт | Заметки знаний, привязанные к ККС, записи, типу или документу | Из оценённых ответов ИИ и вручную, после подтверждения человеком |
| Словарь станции | Термины, сокращения, местные названия и их синонимы | Вручную и из исправлений ответов |

### 8.2 Требования

| Код | Требование |
| --- | --- |
| KNOW-01 | После привязки документа к записи или ККС сервер ставит задачу чтения: текст, таблицы, листы; пользователь видит состояние «в очереди, читается, готово, ошибка» |
| KNOW-02 | Документ делится на фрагменты; каждый попадает в полнотекстовый и векторный индекс и хранит адрес источника |
| KNOW-03 | Найденные в документе коды ККС становятся предложениями связей «ККС ↔ документ ↔ лист»; связь создаётся после подтверждения |
| KNOW-04 | При замене файла индекс пересобирается по хэшу; при удалении документа его фрагменты исчезают из поиска |
| KNOW-05 | Каждый ответ ИИ можно отметить «верно» или «неверно» и исправить; оценка хранится с вопросом, ответом и источниками |
| KNOW-06 | Заметка знаний имеет состояние: предложена, подтверждена, устарела, отклонена. ИИ опирается только на подтверждённые |
| KNOW-07 | Заметка хранит автора, подтвердившего, дату и ссылки на источники с их версиями |
| KNOW-08 | Когда запись или документ-источник изменяется, заметка помечается устаревшей и попадает в очередь проверки |
| KNOW-09 | Право подтверждать заметки — отдельное право роли; есть экран очереди с предложенными и устаревшими заметками |
| KNOW-10 | Словарь расширяет поиск: запрос по местному названию находит объект по официальному коду |
| KNOW-11 | Знания, диалоги и словарь входят в резервные копии и полный пакет экспорта |
| KNOW-12 | Срок хранения диалогов задаёт администратор; пользователь видит и удаляет свои диалоги |

Без KNOW-06 и KNOW-08 память вредит: непроверенные и устаревшие утверждения накапливаются так же, как верные, и ИИ начинает повторять собственные ошибки.

## 9. ИИ-служба

ИИ-служба — отдельный процесс, который отвечает на вопросы по данным базы через инструменты, построенные из схемы типов; модель сменная, а точные запросы выполняются без неё.

### 9.1 Инструменты ИИ

| Инструмент | Что делает |
| --- | --- |
| `schema` | Возвращает доступные пользователю типы, реестры, поля и роли связей |
| `query` | Страница записей реестра по условиям единого языка запросов |
| `aggregate` | Подсчёт, группировка, минимум и максимум средствами SQL |
| `record` | Запись целиком, её история и вложения |
| `kks_resolve`, `kks_card` | Находит объект по коду или псевдониму; возвращает карточку со всеми связанными записями и документами |
| `trace` | Путь по связям между двумя объектами или всё, что связано с объектом |
| `search_documents` | Полнотекстовый и векторный поиск по фрагментам документов и заметкам |
| `sheet_graph`, `sheet_look` | Соединения элемента на листе; описание фрагмента листа моделью зрения |
| `operation_card`, `cable_diagram` | Существующие инженерные инструменты |
| `propose` | Создаёт предложение: правка записи, связь документа с ККС, заметка знаний, сопоставление столбцов Excel |

### 9.2 Требования

| Код | Требование |
| --- | --- |
| AI-01 | Модель подключается через один адаптер: чат с инструментами, векторы текста, зрение. Смена модели — настройка, без изменения кода. По умолчанию используется локальный Ollama |
| AI-02 | Список инструментов и их описания строятся из схемы типов и реестров; новый реестр доступен ИИ сразу после создания |
| AI-03 | Вопрос с точным кодом ККС, номером или простым фильтром выполняется без модели и укладывается в 300 мс |
| AI-04 | Числа в ответе вычисляет SQL через `aggregate`; модель их не считает |
| AI-05 | Поиск по документам гибридный: полнотекстовый и векторный результаты объединяются в один список; словарь станции расширяет запрос |
| AI-06 | Чат получает контекст интерфейса: открытый реестр, выбранные записи, открытую карточку ККС или лист |
| AI-07 | Каждое утверждение ответа имеет ссылку на запись, документ, лист или заметку; ссылка открывается в инспекторе |
| AI-08 | ИИ не сообщает, что данных нет, пока не выполнен поиск по базе и документам; отсутствие данных и отсутствие доступа различаются в ответе |
| AI-09 | ИИ только читает. Любое изменение оформляется предложением, которое человек принимает или отклоняет в интерфейсе |
| AI-10 | Один ответ ограничен 8 шагами и 24 обращениями к серверу; превышение завершает ответ с пояснением |
| AI-11 | Ответ выводится по мере генерации; видно, какой инструмент выполняется |
| AI-12 | Без модели продукт работает: поиск, карточки, инструменты и точные запросы доступны, чат сообщает об отсутствии модели |
| AI-13 | Набор проверочных вопросов: не менее 150 реальных вопросов с верными ответами; прогон локальный, одной командой |
| AI-14 | Выпуск не допускается, если доля верных ответов ниже, чем в предыдущем выпуске; для вопросов с точным ответом из базы цель — не ниже 95 % |
| AI-15 | Облачная модель выключена; включение доступно только администратору и сопровождается предупреждением, что данные уходят за пределы сети |
| AI-16 | `kks_resolve` и поиск понимают код сигнала: разбирают его по правилам станции (DATA-16) и находят объект и строку сигнала. `trace` идёт по графу объектов, включая ссылки на записи и контакты |

Рост качества ИИ измеряется только набором AI-13. Кратное улучшение ожидается от пяти изменений: более сильной модели, инструментов из схемы, поиска по смыслу, контекста интерфейса и накопленных знаний. Конкретную цифру прироста это ТЗ не обещает.

## 10. Схемы: структура листа и зрение

ИИ работает со схемами на двух уровнях: надёжном — по извлечённой структуре листа, и вспомогательном — через модель зрения, которая смотрит на фрагмент изображения. Ответы второго уровня всегда помечаются как требующие проверки.

| Код | Требование |
| --- | --- |
| VIS-01 | Процесс схем работает постоянно и берёт задачи из очереди; модели распознавания загружаются один раз |
| VIS-02 | Документ разбирается при загрузке, а не в момент вопроса; ход разбора виден пользователю |
| VIS-03 | Поддерживаются векторные и сканированные PDF, DXF и изображения; для сканов выполняется распознавание текста |
| VIS-04 | Из векторного PDF и DXF извлекаются надписи с координатами, линии и символы; из них строится граф листа: элементы и соединения |
| VIS-05 | Коды ККС на листе сопоставляются с каталогом; каждое сопоставление имеет уверенность и становится связью после подтверждения человеком |
| VIS-06 | ИИ отвечает по графу листа: что соединено с элементом, по какому пути, на каких ещё листах встречается объект |
| VIS-07 | Модель зрения получает фрагмент листа высокого разрешения вокруг нужного элемента, а не целый лист |
| VIS-08 | Ответ модели зрения показывает фрагмент с рамкой и пометку «по изображению, проверьте»; в базу он попадает только как предложение |
| VIS-09 | Просмотр листа: масштаб, перемещение, маркеры ККС, подсветка найденного пути; щелчок по маркеру открывает карточку |
| VIS-10 | Повторный разбор того же файла не выполняется: результат хранится по хэшу файла и версии разборщика |
| VIS-11 | Качество измеряется на контрольном наборе листов станции: доля найденных ККС и доля верных соединений. Результат не хуже, чем у нынешнего Visual на том же наборе |

Ограничение, которое нужно принять заранее: соединения надёжно извлекаются из векторных файлов. На плотных сканированных чертежах и распознавание, и модель зрения ошибаются; для них результат — подсказка инженеру, а не факт.

| Файлы и документы | Вложения, типы документов, связи с записями, выдержки | Перенос и индекс знаний | 2 |

| Табель | Табель и его настройки | Перенос отдельным модулем | 3 |

Три правила паритета:

1. **Реестр функций.** Файл `docs/features.md`: каждая функция — строка с модулем-источником в старом коде, волной, приёмочным сценарием и состоянием. Реестр составляется на этапе 0 по маршрутам и экранам трёх репозиториев и согласуется владельцем.
2. **Перенесено — значит проверено.** Функция считается перенесённой, когда её сценарий проходит на данных, импортированных из рабочей базы Local\_DB.
3. **Не переносится то, что функцией не является.** Два лишних поколения чата, файлы-заплатки интерфейса, дубли маршрутов, одноразовые workflow, тесты по тексту исходников.

Серверные модули прав, аудита, копий и файлов берутся из пакета `core` Local\_DB и адаптируются к новому хранению; с нуля они не пишутся.

## 14. Импорт базы Local\_DB

Импорт старой базы — штатная функция продукта: администратор указывает каталог данных Local\_DB или её резервную копию, видит отчёт пробного прогона и переносит всё в LOCALAI. Старая база при этом не изменяется.

### 14.1 Ход импорта

1. **Источник.** Каталог данных Local\_DB или шифрованный пакет резервной копии с паролем.
2. **Пробный прогон.** Без записи: версия схемы источника, число записей по режимам, поля, справочники, ККС, файлы, роли, список конфликтов.
3. **Решения.** Соответствие режимов реестрам, площадка, спорные ККС, соответствие ролей.
4. **Перенос.** Данные, история, файлы, права; перед началом создаётся защитный снимок LOCALAI.
5. **Сверка.** Отчёт «было и стало» по каждому реестру; запуск фонового чтения документов и разбора схем.

### 14.2 Требования

| Код | Требование |
| --- | --- |
| MIG-01 | Импорт доступен в мастере первой настройки и в разделе администрирования; запускать его может только администратор |
| MIG-02 | Источник открывается только на чтение; ни один файл Local\_DB не меняется |
| MIG-03 | Поддерживаются схемы баз Local\_DB, которые реально используются; их перечень фиксируется на этапе 1. Более старая база получает понятный отказ с указанием, до какой версии её обновить |
| MIG-04 | Таблица `equipment` с режимами превращается в типы и реестры; поля, в том числе пользовательские, и справочники переносятся с теми же названиями |
| MIG-05 | UUID записей, номера версий, история изменений, признак архива и журнал сохраняются |
| MIG-06 | Каталог ККС строится из полей ККС записей по магниту ККС (IMP-13); одинаковый код в разных режимах даёт один объект, код сигнала не становится объектом каталога. Похожие, но не совпадающие коды не объединяются автоматически и выносятся на разбор |
| MIG-07 | Файлы переносятся с проверкой SHA-256; документы, их типы и привязки к записям сохраняются |
| MIG-08 | Роли Local\_DB и их права по таблицам, полям и документам становятся ролями LOCALAI. Учётные записи создаёт администратор: в Local\_DB персональных пользователей нет |
| MIG-09 | Имена авторов в перенесённой истории остаются текстом с пометкой «из Local\_DB» |
| MIG-10 | Переносятся проверки и акты, табель, профили экспорта, настройки инженерных инструментов, список разрешённых IP |
| MIG-11 | Повторный импорт той же базы не создаёт дублей: записи сопоставляются по UUID. Пока Local\_DB работает параллельно, можно дозагружать изменения |
| MIG-12 | Сбой на любом шаге возвращает LOCALAI к защитному снимку; частичного импорта не бывает |
| MIG-13 | Отчёт сверки сравнивает по каждому реестру число записей, версий, файлов и контрольные суммы значений; расхождение останавливает импорт |

## 15. Поставка, выпуск и CI

Продукт ставится одним установщиком и имеет одну версию; тяжёлые запуски GitHub Actions возможны только вручную и только после локального прогона той же проверки.

| Код | Требование |
| --- | --- |
| REL-01 | Один установщик Windows: сервер, интерфейс, ИИ-служба; процесс схем — компонент по выбору. Модель ИИ в установщик не входит |
| REL-02 | Установка спрашивает режим (один компьютер или сервер сети), пароль администратора и создаёт сертификат сервера |
| REL-03 | Мастер первой настройки: импорт базы Local\_DB, подключение модели, создание первых пользователей |
| REL-04 | У всех компонентов одна версия; совместимость компонентов между собой не настраивается и не проверяется пользователем |
| REL-05 | Обновление сохраняет данные: перед ним создаётся проверенная копия; неудачное обновление откатывается к прежней версии |
| REL-06 | Панель управления на сервере: запуск и остановка служб, их состояние, адрес для рабочих мест |
| CI-01 | На pull request запускается одна лёгкая проверка на Linux до 5 минут: стиль кода и быстрые тесты. Устаревший запуск отменяется |
| CI-02 | Полный набор тестов и сборка установщика запускаются только вручную, по явной команде владельца |
| CI-03 | Перед ручным запуском та же проверка выполняется локально одной командой; запуск без успешного локального прогона запрещён |
| CI-04 | Изменения документов, макетов и текстов не запускают CI |
| CI-05 | Одноразовые workflow не создаются: разовая проверка — параметр единственного ручного workflow |
| CI-06 | Артефакты хранятся 3–5 дней |
| CI-07 | После разрешённого запуска составляется отчёт: коммит, задания, итог, ссылка, наличие установщика |
| CI-08 | Рабочая ветка одна — `main`; задачи ведутся в коротких ветках и вливаются через pull request |

Репозиторий LOCALAI сейчас публичный и пустой. До первого push нужно решить, остаётся ли он публичным: в него переносится код закрытого Local\_DB. По [документации GitHub](https://docs.github.com/en/billing/concepts/product-billing/github-actions) стандартные runner для публичных репозиториев, насколько известно, бесплатны; это нужно проверить на странице оплаты аккаунта.

## 18. Разделение работ между Codex и Claude

Работа делится по границам компонентов: Claude ведёт данные, сервер и ИИ, Codex — интерфейс, процесс схем и поставку. Между ними лежит контракт, который меняет только его владелец.

Основание деления — связность кода, а не сравнение способностей двух ИИ: оно в этом ТЗ не оценивалось. Части Claude делят общие правила транзакций и прав, части Codex зависят только от контракта; контекст двух аудитов уже накоплен в проекте Claude. Назначение можно поменять целиком, но нельзя делить один компонент между двумя исполнителями.

### 18.3 Правила совместной работы

1. **Контракт раньше кода.** Часть контракта для этапа сливается в `main` до того, как оба исполнителя начинают этап.
2. **Один исполнитель на каталог.** Чужой каталог не правится; нужное изменение оформляется запросом в `docs/requests/`.
3. **Формат задачи.** Номер, коды требований этого ТЗ, разрешённые каталоги, приёмочный сценарий. Одна задача — одна ветка (`claude/…` или `codex/…`) — один pull request.
4. **Перекрёстная проверка.** Работу Claude проверяет Codex, работу Codex — Claude; слияние выполняет владелец.
5. **Общая память — файлы репозитория.** Исполнители не видят диалоги друг друга. Правила лежат в `docs/RULES.md`, состояние — в `docs/STATE.md`; оба файла инструкций (`CLAUDE.md` и `AGENTS.md`) ссылаются на них и не дублируют текст.
6. **Состояние обновляется в каждом pull request.** Что сделано, что проверено, что осталось, какие решения приняты.
7. **Политика CI общая.** Ни один исполнитель не запускает тяжёлый workflow и не делает push, который его вызовет, без команды владельца.
8. **Спорное решает владелец.** Противоречие в ТЗ или между исполнителями не решается молча: задача останавливается с вопросом.
9. **Никто не принимает свою работу.** Состояние «принято» ставит владелец по пройденному сценарию.

Имя файла инструкций для Codex нужно сверить с его документацией при создании репозитория.
