# Правила репозитория LOCALAI

Этот файл — общая память двух исполнителей, Claude и Codex. Они не видят диалоги друг друга, поэтому всё, что должно пережить один сеанс, записывается сюда или в [STATE.md](STATE.md). Источник требований — [TZ.md](TZ.md); при расхождении правил и ТЗ задача останавливается с вопросом владельцу.

## 1. Расход GitHub Actions

Главный приоритет проекта — не тратить минуты GitHub Actions.

1. Ни один исполнитель не запускает workflow и не делает push, который его запустит, без явной команды владельца на этот конкретный запуск.
2. Перед каждым push исполнитель проверяет, какие workflow он вызовет, и пишет это в сообщении владельцу. Пока в репозитории нет каталога `.github/workflows/`, push ничего не запускает.
3. Проверки выполняются локально: `python -m pytest tests/engine` и далее по мере появления компонентов. Локальный прогон минут не тратит.
4. Полный набор тестов и сборка установщика в Actions запускаются только вручную владельцем, и только после успешного локального прогона той же командой (CI-02, CI-03).
5. Изменения документов, макетов и текстов не запускают CI (CI-04). Это задаётся фильтром путей в самом workflow, когда он появится.
6. Одноразовые workflow не создаются; разовая проверка — параметр единственного ручного workflow (CI-05).
7. Устаревший запуск отменяется (`concurrency` с `cancel-in-progress`); артефакты хранятся 3–5 дней (CI-06).
8. Упавший или отменённый запуск не перезапускается без команды владельца.
9. После разрешённого запуска — отчёт: коммит, задания, итог, ссылка, наличие установщика (CI-07).
10. Связанные изменения идут одним коммитом и одним push, а не серией мелких.

## 2. Зоны ответственности

У каждого каталога один исполнитель. Чужой каталог не правится: нужное изменение оформляется запросом в [requests/](requests/README.md).

| Каталог | Что в нём | Исполнитель |
| --- | --- | --- |
| `engine/`, `tests/engine/` | Хранение: схема базы, миграции, слой запросов | Claude |
| `server/`, `tests/server/` | Сервер: API, права, импорт и экспорт, копии, аудит | Claude |
| `server/localdb_import/` | Импортёр базы Local_DB | Claude |
| `ai/`, `tests/ai/` | ИИ-служба, память, набор проверочных вопросов | Claude |
| `docs/contract/` | Контракт: API, база, язык запросов, протокол процесса схем | Claude; Codex подаёт запросы |
| `web/` | Интерфейс и дизайн-система | Codex |
| `vision/` | Процесс схем: распознавание, PDF, DXF, граф листа | Codex |
| `packaging/`, `.github/` | Установщик, панель управления, workflow | Codex |
| `tests/e2e/`, `tools/` | Сценарии в браузере, генератор данных, замеры скорости | Codex |
| `docs/` (кроме `contract/`) | ТЗ, реестр функций, состояние, правила | Общий: каждый правит строки своих задач |

Корневые файлы (`README.md`, `pyproject.toml`, `.gitignore`, `CLAUDE.md`, `AGENTS.md`) меняются только отдельной задачей, согласованной с владельцем.

## 3. Порядок работы

1. **Контракт раньше кода.** Часть контракта для этапа попадает в `main` до начала этапа. Интерфейс пишется по контракту и может работать на заглушке, пока сервер не готов.
2. **Одна задача — одна ветка — один pull request.** Ветки называются `claude/<задача>` и `codex/<задача>`. В `main` напрямую не пишут; исключение — первый коммит пустого репозитория.
3. **Формат задачи:** номер из [STATE.md](STATE.md), коды требований ТЗ, разрешённые каталоги, приёмочный сценарий.
4. **Перекрёстная проверка.** Работу Claude проверяет Codex, работу Codex — Claude. Слияние выполняет владелец.
5. **Состояние обновляется в каждом pull request:** что сделано, что проверено и чем, что осталось, какие решения приняты.
6. **Никто не принимает свою работу.** Отметку «принято» ставит владелец по пройденному сценарию.
7. **Спорное решает владелец.** Противоречие в ТЗ, в контракте или между исполнителями не решается молча.
8. **Честный отчёт.** В отчёте различается «проверено запуском» и «написано, но не запускалось». Нельзя писать, что тест пройден, если он не запускался.

## 4. Правила кода

| Код | Правило |
| --- | --- |
| ARCH-01 | `engine` не импортирует `server`, `ai`, `vision`. Проверяется тестом |
| ARCH-02 | ИИ-служба и процесс схем не открывают файл базы; данные идут только через API |
| ARCH-03 | Функция не длиннее 150 строк, модуль не длиннее 800 строк. Проверяется тестом |
| ARCH-04 | Маршруты объявляются по модулям областей; обработчик получает сервисы через явные зависимости, а не из общего состояния приложения |
| ARCH-05 | В именах модулей и файлов нет номеров версий, дат и слов «patch», «fix», «hotfix» |

Дополнительно:

- **Одно действие — одна транзакция.** Изменение, история, связи, индекс поиска и строка аудита пишутся вместе или не пишутся вовсе.
- **Связи по ID.** Названия типов, полей, реестров, ролей и коды ККС только отображаются; переименование ничего не ломает.
- **Сервер — единственный, кто пишет в базу.**
- **Ошибка для человека.** Код, текст на русском, поле или строка, к которым она относится.
- **Тесты проверяют поведение**, а не текст исходного кода. Исключение — три проверки правил ARCH.
- **Без заплаток.** Исправление вносится в то место, где ошибка, а не отдельным слоем поверх.
- **Секретов в репозитории нет:** ни паролей, ни ключей, ни рабочих баз, ни персональных данных.
- **Код из закрытых репозиториев Local_DB, Core и Visual дословно не копируется**, пока этот репозиторий публичный и владелец не решил иначе. Функции переносятся по [features.md](features.md) новой реализацией.

## 5. Язык

Документы, сообщения об ошибках и тексты интерфейса — на русском. Имена в коде — на английском. Комментарии объясняют причину решения, а не пересказывают код.
