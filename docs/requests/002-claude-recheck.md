### 1. Жёсткая ссылка на источник проходит проверку пути отчёта

**Серьёзность** «теряются или портятся данные». MIG-02, перепроверка № 2.

```python
import os
from pathlib import Path
from tempfile import TemporaryDirectory

from server.localdb_import.__main__ import main
from tests.server.localdb_fixture import LocalDb

with TemporaryDirectory() as folder:
    root = Path(folder)
    source = LocalDb(root / "local_db.sqlite3")
    source.field("qty", "Количество", "integer")
    source.record({"qty": 1})
    source.close()

    report = root / "report.json"
    os.link(source.path, report)
    assert report.samefile(source.path)
    print(main([str(source.path), "--report", str(report)]))
    print(source.path.read_bytes()[:23])
```

Получены код выхода `0` и начало `b'{\n  "mode": "dry_run",\n'` у исходной базы. Импортёр сравнивает разрешённые пути, а два имени жёсткой ссылки указывают на один файл. До открытия отчёта нужно проверить идентичность существующих файлов и отклонять совпадение с исходной или целевой базой. [Проверка пути и запись отчёта](../../server/localdb_import/__main__.py)

### 2. Число из JSON округляется до проверки точности

**Серьёзность** «теряются или портятся данные». DATA-02, API-08, перепроверка № 3.

Создать поле `num` вида `number` и отправить сырое тело запроса `POST /api/v1/datasets/D/records`. Пример тела — `{"values":{"num":9007199254740993.0}}`. Числовой литерал должен присутствовать в переданных байтах именно в указанном виде.

| Значение в `values.num` | Получено |
| --- | --- |
| `"9007199254740993"` | `201`, сохранено `9007199254740993` |
| `9007199254740993.0` | `201`, сохранено `9007199254740992` |
| `0.100000000000000005` | `201`, сохранено `0.1` |
| `"0.100000000000000005"` | `400 value_precision`, поле `num` |

`json.loads` переводит дробный литерал во `float` до валидации. К моменту проверки исходная точность уже потеряна. Ожидается точное сохранение допустимого числа либо ошибка с полем при потере точности. [Декодирование запроса](../../server/api.py) · [Проверка числа](../../engine/validation.py)

### 3. Пробный прогон с существующим target создаёт файлы и может прочитать другую базу

**Серьёзность** «неверное поведение». Шаг 2 раздела 14.1 ТЗ, перепроверка № 10.

1. Перенести одну синтетическую запись в `обычная.sqlite3`, закрыть базу и сделать побайтовую копию `подготовленная #01.sqlite3`.
2. Запустить без `--apply` по одному пробному прогону с каждым файлом в `--target`. Сохранить отчёты с `--report` и сравнить сводки.

| Имя целевой базы | Сводка | Файлы после прогона |
| --- | --- | --- |
| `обычная.sqlite3` | `records_new=0`, `records_unchanged=1` | Появились `обычная.sqlite3-wal` и `обычная.sqlite3-shm` |
| `подготовленная #01.sqlite3` | `records_new=1`, `records_unchanged=0` | Появился пустой файл с именем `подготовленная ` |

CLI формирует URI SQLite из пути без экранирования. `#` обрезает имя и параметры URI. Для обычного имени режим `mode=ro` на закрытой WAL-базе создал служебные файлы. Пробный прогон должен прочитать указанный файл и сохранить состав его каталога. [Создание рабочей копии цели](../../server/localdb_import/__main__.py)

### 4. Курсор перебирает группу одинаковых значений

**Серьёзность** «неверное поведение». API-05, перепроверка № 19.

1. Создать поле `rank` вида `integer` с `sortable=true`. В первом реестре записать 10 000 разных рангов `0…9999`, во втором 10 000 записей с `rank=1`.
2. По каждому реестру получить курсор после 48 страниц по 200 строк. Использовать `desc` для обоих реестров и повторить с `asc` для равных рангов.
3. Сравнить первую страницу и страницу после курсора с `limit=5`. Использовать `conn.set_progress_handler(callback, 100)` и `EXPLAIN QUERY PLAN` для SQL, снятого через `conn.set_trace_callback`.

| Нагрузка | Сортировка | Вызовы обработчика на первой странице | Вызовы после 9 600 записей |
| --- | --- | ---: | ---: |
| Разные ранги | `desc` | 1 | 3 |
| Одинаковый ранг | `desc` | 2 | 770 |
| Одинаковый ранг | `asc` | 2 | 772 |

Курсор вернул нужные UUID. План глубокой страницы использовал диапазон по `json_extract` в `ix_doc_rank`, при этом обработчик SQLite зафиксировал обход внутри группы одинакового `rank`. Переход должен учитывать позицию по `seq` внутри группы с равным ключом. [Условия продолжения после курсора](../../engine/query.py) · [Контракт сортировки и страниц](../contract/query-language.md#сортировка-и-страницы)

### 5. Повреждённое содержимое курсора вызывает 500

**Серьёзность** «неверное поведение». API-04 и API-08.

На реестре с двумя записями и числовым `rank` получить `next_cursor` при `limit=1` и `sort={"field":"rank","dir":"desc"}`. Декодировать курсор из URL-safe Base64 как JSON-массив `[tag, value, seq]`. Сохранив `tag`, по отдельности подставить объект `{}` вместо `value` и число `9223372036854775808` вместо `seq`. Закодировать массив обратно и передать в `POST /api/v1/datasets/D/records/query` с исходной сортировкой.

Оба запроса вернули `500 internal`. Объект в значении курсора дошёл до привязки SQL-параметров, а `seq` превысил диапазон SQLite. Ожидается `400 query_invalid` с указанием курсора. [Декодирование курсора и привязка параметров](../../engine/query.py)

### 6. Маршрут без схемы тела пропускает лимит 10 МиБ

**Серьёзность** «неверное поведение». API-08, перепроверка № 14.

Под Uvicorn на `127.0.0.1` создать действующее поле `F`. С `Content-Type: application/json`, фактическим `Content-Length` и отдельными ключами идемпотентности отправить одно тело `b'{"name":"' + b'a' * (10 * 1024 * 1024) + b'"}'` на `POST /api/v1/sites` и `POST /api/v1/fields/F/archive`.

`/sites` вернул `413 application/json` с кодом `request_too_large`. Маршрут архива вернул `200 application/json` с заполненным `archived_at`. Оба результата совпали при прогоне через ASGI. Чтение с лимитом начинается после проверки наличия схемы тела. Общий лимит должен срабатывать до выполнения изменяющего маршрута.
